# Architecture of the repo analysis tool

This note records the decisions that would be expensive to change later. It covers the repo analysis tool only. The generator and the doctors' sandbox will be described when we reach them. Every table and column name in this note is invented.

## The parts

```
core/        A Python package, schemalyser, which depends only on sqlglot.
site/        The page, written in TypeScript and built with Vite.
fixtures/    The invented catalogue, the invented requests and the planted values.
```

The core holds all of the analysis. It runs unchanged in two places: natively under pytest, and in the browser under Pyodide. The page does no analysis of its own.

In the browser the core runs inside a single web worker. The page reads the files the user selects and passes their contents to the worker. The worker returns only two things, which are the finished inventory pack and the coverage counts. The contents of the requests never return to the page.

## Where an output string comes from

The tool never copies a string from a request into the inventory pack. Every string it writes comes from one of four places:

- the catalogue file, for table and column names;
- the checks file, for confirmed category values and definition identifiers;
- the site rules file;
- a fixed vocabulary in the code, covering SQL keywords, operators, built-in function names and placeholders.

When the core meets a name in a request, it looks the name up in the catalogue and writes the catalogue's own spelling. A name that is not in the catalogue has nothing to be looked up to, so it cannot be written. The same holds for a literal value and the checks file. This rule is enforced where a finding is first recorded and again where the pack is written.

The check script is a separate kind of output, which goes only to the analytics team, and it follows the same rule. It is built from catalogue names and fixed text, so it carries nothing from the requests. A check on a column that the site rules name as a definition key reads its labels from the definition table when the script runs, and the script never holds the identifiers that the requests compare against that column.

## Findings

The core turns each statement into plain records called findings. A finding does not depend on the parser, so the parser can be replaced without changing anything downstream.

| Finding | What it records |
|---|---|
| Table use | A request uses a catalogue table. |
| Column use | A request uses a catalogue column, and whether it selects, filters, joins, groups or derives from the column. |
| Join | Two catalogue columns are compared across tables, and the kind of join. |
| Filter | A catalogue column is compared with a value, the operator, and either a placeholder or a confirmed value. |
| Derivation | A computed expression, rebuilt from catalogue columns, placeholders, operators and built-in functions. |
| Unresolved | A statement or a part of one that the core could not analyse, with a category from a fixed list. |

## The inventory pack

Each file is plain text, sorted in a stable order so that two runs over the same inputs give identical files.

| File | Columns |
|---|---|
| `elements.csv` | table, column, data_type, requests, selected, filtered, joined, grouped, derived |
| `joins.csv` | left_table, left_column, right_table, right_column, join_kind, requests |
| `filters.csv` | table, column, operator, value_kind, value, requests |
| `derivations.csv` | expression, columns, requests |
| `requests.csv` | request, statements, unresolved, elements |
| `coverage.txt` | plain sentences giving the number of files read, what was found, and a count for each kind of thing that could not be read |

In `requests.csv` a request is identified by a number. The page shows which file each number refers to, and that mapping is not part of the pack.

A request file is counted as not read in full when part of it could not be parsed, when it builds SQL as text when it runs or calls a stored procedure, when it holds a statement of a kind that the analyser does not analyse, or when the analyser could not match the columns of one of its queries to their tables, because in each case the evidence for a join or a filter may lie in the part that the analyser could not see. The coverage, the boundary's summary and the checklist of a target query all count by this one rule, which `vocabulary.not_fully_read` holds, and each says what it counts.

## Names that are accepted

A table, column or schema name is accepted from the catalogue only if it is a plain name: letters, digits, spaces and the characters `_ $ # @`, beginning with a letter or an underscore. A row with any other name is left out. Names are written into the check script and into the sandbox's statements, and this rule, with quoting as a second defence, is what stops a damaged or hostile catalogue from putting SQL of its own into either. A table name that appears in two schemas is left out as well, because a request does not say which is meant.

## The site rules file

The site rules file is JSON, written by the clinical lead and loaded at run time. It carries everything the tool needs to know about one site's naming, so that the code carries none of it.

```json
{
  "definitionKeys": [
    { "column": "OBS_TYPE_KEY", "definitionTable": "OBS_TYPE_DEF", "labelColumn": "OBS_LABEL" }
  ],
  "personTables": ["PERSON_MASTER", "STAFF_MASTER"],
  "localTablePatterns": ["X_%"],
  "sentinelValues": [{ "dataType": "datetime", "value": "2157-11-19" }]
}
```

The tool never generates a definition lookup against a table listed under `personTables`.

The site rules file can also say what a column means, so that the sandbox can fill it with realistic values. Each entry under `roles` names a column and one meaning from a fixed list: `birth_date`, `sex`, `event_time`, `weight`, `height`, `heart_rate`, `respiratory_rate`, `systolic_pressure`, `diastolic_pressure`, `mean_pressure`, `oxygen_saturation`, `temperature`, `medication_name`, `anaesthetic_start`, `anaesthetic_stop`, `blood_pressure` (text such as 110/70), `end_tidal_co2`, `end_tidal_agent`, `administration_time`, `time_during_anaesthetic`, `placement_time`, `removal_time`, `admission_time`, `discharge_time`, `procedure_name`, `diagnosis_code`, `death_date`, `cuff_mean_pressure` and `arterial_mean_pressure`. For a general-purpose table, an entry says which identifier beside the value it applies to.

```json
"roles": [
  { "table": "PERSON_MASTER", "column": "BIRTH_TS", "role": "birth_date" },
  { "table": "PERSON_MASTER", "column": "SEX_CAT", "role": "sex", "values": { "male": "1", "female": "2" } },
  { "table": "THEATRE_CASE", "column": "CASE_DATE", "role": "event_time" },
  { "table": "OBS_READING", "column": "READ_VALUE", "role": "weight", "unit": "oz",
    "when": { "column": "OBS_TYPE_KEY", "equals": "14" }, "at": "READ_TS" }
]
```

The roles are written into the inventory as `roles.csv`, and the sandbox checks every row again when it reads them. The values themselves come from reference data kept in `core/schemalyser/realism/`: the CDC growth charts for weight and height by age and sex, published ranges for heart rate, respiratory rate and blood pressure by age, a list of generic medication names, and short lists of common operations and ICD-10 codes written for this project. `SOURCES.md` in that folder gives the origin and terms of each file. Nothing in that folder comes from any hospital.

Where an entry names the column that holds the time of the value, with `at`, and the rules also give the start and the end of an anaesthetic, the sandbox places each timed value around the anaesthetic that its row belongs to. Row i of a table belongs to anaesthetic i modulo the number of anaesthetics, as a key to the table of anaesthetics would, so a child with two anaesthetics has the values of each placed around that anaesthetic, and the child's date of birth falls before both. Where the check results hold a fanout result, the rows follow the keys instead, as the section on fanout checks describes. A column with the meaning `event_time` in another table is set to the day of the anaesthetic. A weight or a height falls in the day before the anaesthetic starts, and every other value falls while it runs. A column with the meaning `administration_time` is placed the same way, with half of the doses in the first quarter of an hour, as at induction. A `time_during_anaesthetic` falls anywhere while the anaesthetic runs, a `placement_time` in its first quarter of an hour, and a `removal_time` in its last ten minutes. An `admission_time` falls one to two days before the anaesthetic and a `discharge_time` within three days after it. The times then no longer follow the year counts from the check results for that column.

Every number in the paragraph above, and every other timing and distribution that the realistic values use, is a tunable parameter listed in `core/schemalyser/tuning.py` with its default, a description and where the default came from. The site rules file may override any of them under `tuning`:

```json
"tuning": { "anaesthetic_durations_minutes": [45, 60, 90, 150], "still_in_place_share": 0.05 }
```

The tool accepts an override only for a parameter it knows, and only as a number, or a list of numbers, within the bounds that the parameter allows. It ignores anything else. The accepted overrides are written into the inventory as `tuning.csv`, and the sandbox checks them again when it reads them. Where the rules give `sentinelValues`, the first date among them is the removal time of an airway or a line that is still in place, and `still_in_place_share` sets how many of them are. Its default is none.

Two roles add readings of their own rather than fill a column, because a monitor charts a mean pressure as a numeric reading beside the others. Each names, with `when`, the code that marks its readings and, with `at`, the column that holds their time. A `cuff_mean_pressure` adds, beside each charted blood pressure of the same table, a copy of that row with the cuff mean's code, the same time, and the diastolic and a third of the difference to the systolic as its value. An `arterial_mean_pressure` adds, for a share of the anaesthetics, a copy of the first row of the table that belongs to the anaesthetic, once every few minutes from its start to its end, with a value drawn from the reference mean pressure for the child's age around a level that holds through the anaesthetic. The share (`arterial_line_share`, 0.15 by default), the interval (`arterial_interval_minutes`, one minute) and the lowest and highest mean pressure (`mean_pressure_lowest` and `mean_pressure_highest`, 20 and 120 mmHg) are tunable parameters. The sandbox adds these readings only where the check results list their code, because only then does the source hold such readings, and it leaves that code out when it draws the values of the column, so that the other readings are drawn exactly as before. The rows it adds are counted among the rows it built. In the reference data a newborn's mean pressure under anaesthesia has a median of about 35 mmHg, so many of the neonatal readings fall below 40.

A role that the sandbox cannot apply leaves the filler in place. The sandbox lists each such role by its table, column and role name, with a reason from a fixed list, and never with the text of a database error.

## Spans checks

The check script can also count, for a pair of date columns in one table, the rows by the number of minutes from the first column to the second. The pairs are those that the requests compare, and those that the site rules give the paired roles `anaesthetic_start` and `anaesthetic_stop`, `admission_time` and `discharge_time`, or `placement_time` and `removal_time`, in a table that the requests use. The counts fall in fixed bands, from `less than zero minutes` to `a week or more`, whose labels are the only values a result may hold. A result row has the kind `spans`, the first column under `column_name`, the band under `value` and the second column under `label`. The same safeguards apply as to the other checks: no spans check is planned for a table of people or a key to a person, counts are rounded down to ten, a band with fewer rows than the minimum is left out, and every row is checked again when the results are read. The script includes these checks by default, and the boundary's options can leave them out.

The minimum count applies to rows and not to people, so one person with ten or more rows in a table can fill a band alone. The counts are rounded down, not randomised, so that two runs can be compared.

The script sets `ANSI_WARNINGS` off, so that SQL Server does not print a warning among the results when an aggregate passes over empty values; a test on SQL Server 2022 confirmed that `INSERT ... SELECT` with such an aggregate prints one otherwise. When the results are read, a line that is exactly such a message is passed over, and any other line out of place still refuses the file. A values check for a definition key reads the definition table for labels, so the inventory lists every such table in `checked.csv`, and the sandbox builds it even where no request reads it.

Where the check results give the spans from the start to the stop of the anaesthetic, the sandbox draws each anaesthetic's duration from those bands in proportion to their counts, and the tunable parameter reports the check results as its provenance. Spans from placement to removal, and from admission to discharge, set those intervals in the same way, although a discharge still falls after the anaesthetic has ended.

## Fanout checks

The check script can also count, for a column that refers to another table's key, how many key values appear in one row, in two rows, in three to five, in six to ten, and in eleven or more. The columns are those that the requests, or the steps of a conversion, join to a parent column that is unique: the check results say so where they hold a column check for it, and otherwise the catalogue does, when the parent column is the first column of its table and may not be empty. A child column that the check results show to be unique, a column whose values the script lists, and a definition key are left out. A result row has the kind `fanout`, the child's table and column under `table_name` and `column_name`, the band under `value`, the parent as `TABLE.COLUMN` under `label`, and the number of key values under `row_count`. The script counts the rows of each key value in a subquery and returns only the bands, so it never returns a key value. The same safeguards apply as to the other checks: no fanout check is planned where either table describes people or either column is a key to a person, counts are rounded down to ten, a band with fewer key values than the minimum is left out, and every row is checked again when the results are read, with both tables and both columns in the catalogue and the band among the fixed labels. The script includes these checks by default, and the boundary's options can leave them out.

The minimum count applies to key values and not to people. The counts are rounded down, not randomised, so that two runs can be compared. The check deliberately counts the keys of the patient table by their number of visits or anaesthetics, and it returns only how many keys fall in each band, because that distribution is what the check exists to measure. The tables of people that the site rules list, and that the check leaves out, are those such as the staff table whose rows name people, and the patient table is not among them.

Where the check results hold a fanout result for a join that the sandbox builds, the sandbox assigns the child's rows to parents so that the parents with one child, two, three to five and so on are in the proportions of the result, and each parent draws its number of children evenly within its band. A result in which every key value has one row changes nothing. To keep everything else correct, the keys then follow a lineage rather than the positional scheme. Tables that are unique in one key hold the same rows, and form a group. A key that is not unique gives each row of its group a position in the group of the tables in which the key is unique, and through that position the row reaches everything that group reaches. Where two keys of one group reach the same group, the second is chosen to agree with the first, so that a case's patient is always its hospital visit's patient. The realistic values follow the same lineage: each subject's date of birth falls before all of their anaesthetics and of any timed value that has no anaesthetic, a death falls after the last of them, a row below an anaesthetic is placed around its own anaesthetic, and a row above one, such as a hospital visit, is placed around all of its anaesthetics, from the start of the first to the end of the last. A row that reaches its subject but no anaesthetic is placed around the subject's first anaesthetic, and a row of a table that reaches neither keeps the positional scheme. Without a fanout result none of this applies, and the sandbox is built exactly as before.

The lineage does not change the size of any table, so a parent may be left without children, as a patient without an anaesthetic is. A join whose child and parent the other check results show to be one to one elsewhere, through a third table unique in both keys, cannot be skewed, and its fan-out is reported as not applied. For each parent-child join, `Sandbox.fanout` gives after a build whether its fan-out came from the check results, is uniform because there were none, or is uniform because they could not be applied.

The harness takes `--fanout`, which plans these checks and gives the stand-in database a skewed design for every join that they count from a column that does not key its own table. The scorecard then gives, for each join, the shares that the check results asked for and those that the sandbox built.

## What the check script costs the server

The check script is written to be safe and light to run on a production Clarity, and an analyst can read every statement in it before running it.

- **It only reads.** The one thing it creates is a temporary table of its own, which holds its results and goes when the session ends.
- **It takes no row locks.** It reads at `READ UNCOMMITTED`, which still holds a schema lock while each statement runs, so it should not run during the nightly load. It waits no more than ten seconds for a lock that it cannot avoid, and has the low deadlock priority, so it neither holds other work up nor waits behind it. A count can be out by the rows that were changing as it read them, which does not matter, because every count is rounded down to the nearest ten.
- **It does not count the rows of a table.** It takes the number from `sys.partitions`, which costs nothing, and counts only where the server holds no number, as for a view.
- **It is sparing with a large table.** A table with more than `@large_table_rows` rows (100,000,000 unless the analyst changes it) is large. A values, years or spans check reads `@sample_percent` per cent of a large table's pages with `TABLESAMPLE`, scales its counts up, and records a `sampled` row. The least count then applies to the rows of the sample, so a sampled check lists less, never more. A column or fanout check needs every row, so the script leaves it out for a large table and records a `skipped` row with the reason `size`.
- **It stops starting checks when its time is up.** After `@minutes_allowed` minutes (30 unless the analyst changes it) each remaining check is recorded as `skipped` with the reason `time`. The script cannot end a check that is already running, so the limit bounds the number of checks and not the length of the last one.
- **It runs the cheapest and most useful checks first:** the row counts, then the values, spans and years, and last the column and fanout checks, which read every row of a table.
- **Each check fails alone.** A missing table, a refused permission or a lock that did not clear is recorded as an `error` row, and the script goes on.

`Checks.from_csv` reads the `skipped` and `sampled` rows and accepts only the kinds of check and the reasons that the script and the table sizes query can write: `time`, `size` and `unrecorded`. The page and the register of questions say how many checks were left out for time or size and which number the analytics team can raise to run them. The script still reads each table once for each check on it, so a table just under the limit can be read several times; the time allowed is the backstop for that.

## The queries on the checklist

The whole script is no longer the first thing that the tool asks an analyst to run. The checklist of each target query instead gives, beside each open item that check results would settle or help to settle, the plain query that answers it, with a sentence saying what the query counts and why the item needs it. The analyst runs one query in SQL Server Management Studio, pastes its result into the page, and the item ticks. Only the checks that an item of that target needs are offered, and a check that several items need is one query, shown with the first of them. The whole script stays available, unchanged, for a team that prefers one run, and its results can be pasted in the same way.

`Check.plain` writes each check as one static `SELECT` over several short lines, with a comment at its head that says what it counts. It returns the nine columns of the results layout under their own names, so that a result describes itself and `Checks.from_csv` reads it under the same rules as a results file. On the same data it gives the same rows as the script's exact form, which the tests confirm in DuckDB and the SQL Server harness confirmed for every check of the invented world. The query is safe by construction rather than by the analyst's care:

- **It only reads.** It is one `SELECT`, with no variable, no dynamic SQL, no setting, no temporary table and no error handling.
- **It keeps to the privacy rules.** Every count is rounded down to ten and a value or band held by fewer than ten rows is left out, both written into the query as numbers. The checks are planned under the same exclusions as the script's: no values for a table of people, a key to a person, a column named like free text or a long text column. A values query carries `TOP (N + 1)` for the limit N of its column, and lists nothing when the column holds more than N values, as the script's guard does, so that it can never return a long list; `from_csv` refuses a result that reaches the limit.
- **It takes no row locks.** Each table is read `WITH (NOLOCK)`, so the query takes no row locks, but it holds a schema lock while it runs, so it should not run during the nightly load.
- **It is never costly by surprise.** The tool offers no query on a table whose size it does not know, and never reads the whole of a table that it knows to be large.

The first query of each checklist is therefore the table sizes query, `checks.size_query`, for the tables that the checklist's other queries read. It reads `sys.tables` and `sys.partitions`, with `index_id IN (0, 1)`, for a literal list of catalogue names, each with its schema where the catalogue gives one, and reads no table. Each table that the server records comes back as a `rows` result rounded down to ten; a name for which the server keeps no record, such as a view, comes back as a `skipped` row for the kind `rows` with the reason `unrecorded`. Once the sizes are in the check results, `checks.offer` decides how each check is offered:

| The table | What the checklist offers |
|---|---|
| Size not yet known | Nothing but the table sizes query. The item says that it waits for the sizes. |
| Size not recorded by the server | A count of the table, marked as reading the whole of it, and nothing else until the count is in. |
| At or under `PLAIN_EXACT_ROWS` (10,000,000) | The exact query. |
| Larger, for a values, years or spans check | A query over `TABLESAMPLE SYSTEM (p PERCENT) WITH (NOLOCK)`, with p the percentage, a fraction where it must be, that holds about `PLAIN_SAMPLE_ROWS` (5,000,000) rows at any size, and a literal `REPEATABLE` seed, each count scaled up by `* 100.0 / p` as an estimate, the least count applied to the rows of the sample, and one constant row of the kind `sampled`, added with `UNION ALL`, that records the percentage. |
| Larger, for a column or fanout check | No query. The item says that the count needs every row of a large table, how the item can be answered instead where the tool allows it, and that the whole script still counts a table of up to 100,000,000 rows. |

A plain query that can find nothing, which is a values, years, spans or fanout query in its exact form, adds one constant row of the kind `ran`, with `UNION ALL`, that names the check; a sampled query's `sampled` row does the same. `from_csv` accepts a `ran` row only for a catalogue table and column, one of those four kinds, and for a spans or fanout check a second column or parent that the catalogue holds. A check whose query has run and found nothing is therefore recorded as asked and answered with nothing: the checklist does not offer its query again, the item says plainly that the query found no value that ten or more rows hold, and the register counts the check as answered.

A values check for a definition key also reads its definition table, so it waits for that table's size as well. SQL Server 2022 accepts the sampled form with the hint after the sample, as T-SQL's grammar places it, and `TOP` with `UNION ALL` applies to the first `SELECT` alone, as the harness run confirmed.

The checklist, `checklist.csv`, has three more columns for this: `query_state`, which is `ready`, `waiting` or `large`; `query_reason`, the sentences that say what the query counts, why the item needs it, what it waits for, and how the item can be answered without it; and `query`, the text of its queries. Where the tool already lets a person answer an item without a query, the item says so: the clinical lead can write mapping rows for codes, which leaves the item partly answered until the check results list one of the codes, and can give a duration or a share under `tuning` in the site rules, which answers it. The boundary also writes `targets/NAME/queries.sql`, which holds the queries that the checklist offers now, the table sizes query first.

`Checks.from_pasted` reads results pasted from a results grid, which is tab-separated, or from a CSV file, with or without a header row. It passes over a header row wherever it falls, so that the results of several queries can be pasted together, and the count of rows that `sqlcmd` prints, and it then applies `from_csv` unchanged, so that a value from a table of people, a count that is not rounded or is under ten, a table that is not in the catalogue, a formula and a values result that reaches its limit are left out exactly as they are from a file. `Checks.merged` adds later results to earlier ones, and a later result for a check replaces the earlier result as a whole, together with any `sampled` or `skipped` record of the same check. An exact result therefore replaces a sampled one, and a count replaces the record that the server keeps no size. A check that met an error is kept as an `error` row with its table, its column where it has one, and the server's error number, which must be a whole number; `to_csv` writes it back, so that a saved state still says which checks failed. An error row names only the table and the column, so any later result for that table and column, other than a skipped check, replaces the failure, as does a later failure of the same check.

## Loading and safeguards

- **One origin.** Every script, the Pyodide runtime and the sqlglot package are served from the site itself. A content security policy forbids connections to any other origin. The policy allows images only from the site itself, for the page's own icon, so that the browser's request for an icon succeeds and leaves no refusal in the console. The two refusals that do appear in the console come from the worker's own check of the policy, below, and the page says so once it has loaded.
- **The worker inherits the policy.** A static host cannot set the policy for a worker's own file, so the page fetches the worker's code and starts it from a blob. A worker started that way takes on the page's policy.
- **Eager loading.** The page fetches and starts everything as soon as it opens, then reports that it is ready to be taken offline. It is enough to take only the browser tab offline (the developer tools' Network panel in Chrome or Edge, or Work Offline in Firefox), because the page reads the browser's own report of whether it is online, so a SQL window on the same computer stays connected.
- **The offline gate.** The file loader stays disabled until the browser reports that it is offline.
- **The worker holds the requests.** The contents of the requests exist only inside the worker. If the browser reports that it is online again, the page ends the worker at once and offers only two actions, which are to download the pack or to clear it.
- **The worker checks the policy for itself.** Before it starts, the worker asks for an address on another site and watches for the policy to refuse it. If the browser does not report the refusal, the worker does not start. Chromium and Firefox pass this check. WebKit, and so Safari, does not report the policy to a worker started from a blob, so the tool refuses to start there.
- **The worker gives up the network.** Once it has loaded, the worker removes its own means of making a request.
- **The database is shut in.** The sandbox's DuckDB database is set so that it cannot read or write files, reach a network, or load an extension, and so that those settings cannot be changed.
- **A past request leaves nothing behind.** Each past request is run inside a transaction that is rolled back, and its variables are reset, so that nothing from its text stays in the sandbox database.
- **No storage.** The page and the worker use no cookies, no local storage and no other browser storage.
- **A visible version.** The page shows its version and a checksum of its files. The checksum identifies a build. It is served by the same host as the page, so on its own it proves nothing: it is useful only when compared with a value published somewhere else, such as a signed release.

**Fetching from GitHub.** The page also offers to fetch the files from up to two private repositories on GitHub instead of taking them from the computer. The page's own policy does not change and never allows GitHub. The fetch runs in a small window of its own, `github.html`, whose policy allows connections to the site and to `https://api.github.com` and to nothing else. The page passes that window the two repositories, a ref for each and the access token, then empties the token field and keeps no copy. The window first confirms that its policy refuses another site, then resolves each ref to a commit, reads the commit's recursive tree and fetches the blobs, using GET requests only and sending the token only in the `Authorization` header. It takes the files ending in `.sql` from the requests repository, and from Schemalyser's repository the files of the boundary's state folder: `catalogue.csv`, `site-rules.json`, `checks.csv`, `core-profile.csv` and `boundary.json` from its root, everything under `conversion/`, and the `.sql` files directly under `targets/`. It leaves out any file larger than 2 MB, stops at 5,000 files from a repository, and says so when GitHub returns only part of a tree. When the fetch ends, whether or not it succeeded, the window forgets the token, adds a second policy that allows only the site (policies intersect, so the second can only take permissions away), and confirms that GitHub is now refused. Only then does it hand the files and the two commits to the page and close itself; if GitHub is not refused, it hands over nothing. The page passes the fetched files to the worker by the same path as chosen files, and only once the browser is offline. The worker's own check now also confirms that it cannot reach GitHub, so a page whose policy allowed GitHub would not start. The results name the repositories and commits they come from. A file chosen from the computer takes the place of the fetched file of the same kind, and the fetched files are discarded when the network returns after the browser has been offline, or when the page is cleared.

### What these safeguards do not cover

- **A compromised host or dependency.** The policy is part of the page, so a host that has been tampered with can serve a page without it. The worker's own check catches a missing policy, and the offline step limits what such a page could do, but code that waits for the network to return could still send what it holds. The defence is to run a fixed, reviewed release from a host the hospital controls.
- **Browser extensions.** An extension can read what the page shows, including the list of file names. A clean browser profile without extensions avoids this.
- **The names in the site rules.** A definition lookup returns the labels of whatever table the site rules name. If the rules name a table that describes people, the script will list those people. The rules file is written by a person and should be reviewed as carefully as the script.
- **The token while it is in use.** The token is typed into this page, passed once to the fetch window and held there in a variable until the fetch ends. A string in JavaScript cannot be wiped, so overwriting the variable lets go of the token but does not erase it from the browser's memory at once. The field is a password field, and a password manager may still offer to save its contents. While the fetch window is open, the page could in principle reach GitHub through it, because both come from the same site; the page does not analyse anything while the window is open, and the token should be fine-grained, read-only and short-lived.

## The sandbox page

A second page builds a synthetic database from a catalogue file and an inventory. It uses the same worker arrangement and the same content security policy. DuckDB runs inside Pyodide beside the core, and its package is served from the site and checked against the checksum in Pyodide's own lock file when the site is built. The page accepts the folder of requests only while the browser is offline, and it lets go of the file names when the network returns.

## Running a conversion to OMOP

`core/schemalyser/convert.py` runs a conversion over the sandbox. A conversion is a folder that holds `conversion.json`, which lists the steps in order, one `.sql` file for each step, and optionally `source_to_concept_map.csv`, `gates/` and `counts/`, which the section on quality gates describes. Each step is a single T-SQL `SELECT` whose output columns are named as the fields of one OMOP table. A step reads the source tables, and may read an OMOP table that an earlier step wrote, as `omop.<table>`.

Each step names a layer. The `core` layer stands in for an OMOP database that someone else maintains, so that the whole pipeline can be tested here, and it is not meant to run against a real database. The `anaesthesia` layer is the part that is. It finds its people and visits in the OMOP tables, and the runner refuses an anaesthesia step that writes a table belonging to the core alone, such as PERSON or VISIT_OCCURRENCE.

The `derived` layer runs last and also ships. Its steps read only the OMOP tables, and each writes a custom table that the folder's `tables.json` defines, so that the tables of CDM 5.4 stay as the model defines them. For each custom table the file gives its name, a one-sentence description and its fields, each with a name, a type (`integer`, `float`, `date`, `datetime` or `varchar(n)`), whether it is required, whether it is the primary key, and a one-sentence description that states the rule by which the field is derived. A name must be a plain name in lower case, and a table may not take the name of a table of CDM 5.4. A step and a target query read a custom table as `omop.<table>`, like any other. The runner refuses a conversion whose steps are not in the order core, anaesthesia, derived, a derived step that writes anything but a custom table, and any other step that writes one. It creates the custom tables, checks a derived step's output columns against `tables.json`, and reports an empty required field, a repeated primary key and text that is too long for its field, as it does for the CDM tables. A derived step keeps the identifiers it writes, because they are those of the OMOP rows it is built from.

The runner creates the tables of CDM 5.4 from `core/schemalyser/omop/cdm54_fields.csv`, loads the mapping rows, and inserts each step's rows. It refuses a step that names a field the table does not have, and a step whose file name holds anything but letters, digits, full stops, hyphens and underscores. It then reports any required field that is empty, any primary key that is repeated and any text longer than its field allows, and writes one CSV file for each table that holds rows, with a `load_postgresql.sql` script that loads those files with `psql`.

The command exits with 1 when a step does not run cleanly, when a gate fails or cannot be run, when a count cannot be run, or when any problem is reported. A problem includes a derived mapping whose table or columns the sandbox does not hold, and a step that the analysis could not read as one `SELECT`, because either would otherwise leave the sandbox without values that the steps need. With `--checks FILE`, the sandbox is built from those check results, such as the hospital's own, instead of from answers computed over the stand-in database.

The conversion's own SQL is analysed with the requests, so that the sandbox builds the tables it reads. Each source column that a step looks up in the mapping table is treated as a filtered column, so that the checks list its values under the same rules as any other column, and the sandbox then holds the same codes as the real database. For that analysis each step is rewritten as a `SELECT ... INTO` a temporary table, so that the analysis follows a key through an OMOP table back to the source column it was copied from.

    python -m schemalyser.convert WORLD CONVERSION --out OUT [--checks CHECKS.csv]

A conversion folder may also hold `derived_mappings.json`. Each entry names a table of local codes with their labels, such as the medication definitions. With `--vocabulary`, the runner looks each label up by name in the Athena download and adds a mapping row for each label that matches a single standard concept. `core/schemalyser/mapping.py` does the lookup, and it can be run by itself over a file of codes and labels to give a first pass of mapping rows for a person to review. A label matches through its name, a synonym, or a concept that maps to the standard one, which is how an Australian name such as paracetamol reaches its RxNorm ingredient. An entry may instead say that its labels are codes of a named vocabulary, such as ICD-10, and each code is then followed to the standard concept it maps to.

With `--vocabulary`, the runner also checks every concept it wrote against `CONCEPT.csv` from an Athena download. A concept must be in that file, be a standard concept, and belong to the domain that CDM 5.4 expects of its field. Rows written with the concept 0 are counted, because each one is a value that has not been mapped.

`fixtures/conversion/` holds a conversion for the invented catalogue: people, hospital visits, the anaesthetic as a visit detail, the anaesthetic as a procedure, measurements, single doses of medicines, and the observation period. The measurement step writes every accepted numeric reading in the anaesthetic's own record, which is an observation sheet that carries the key of an anaesthetic that the layer has written. A reading whose observation type has no mapping row takes the concept 0 and keeps its observation type as `measurement_source_value`, so that a mapping row added later gives those rows their concept on the next run. A reading elsewhere is written only when its type has a mapping row, a value that is not a number is written only where a mapping row gives it a meaning, and the step writes metric units whatever unit the source holds. The run reports how many measurement rows have no mapping row and from how many variables, as counts only, and the command writes `unmapped_measurements.csv`, which lists those variables by their source identifier as a worklist for the mapping rows, for use inside the hospital only. A mean pressure that the monitor charts as a reading of its own is written by the measurement step through mapping rows alone: the mean from the cuff with the concept 21492241 (Mean blood pressure by Noninvasive, LOINC 76536-2) and the mean from an arterial line with the concept 21490852 (Invasive Mean blood pressure, LOINC 76214-6), each in mmHg (8876). The step numbers its rows by sheet and line and then by time and value, because a monitor can chart many readings under one line. A second measurement step splits a charted blood pressure, held as text such as 110/70, into a systolic and a diastolic row. A third, `measurement_mean_pressure_calculated.sql`, can write for each charted pressure that gives both a systolic and a diastolic row a mean calculated as the diastolic and a third of the difference, with the concept 3027598 (Mean blood pressure), the type concept 32882 (Standard algorithm from EHR), which marks it as calculated, the unit 8876 and the same links to the anaesthetic as the blood pressure step gives. It writes nothing unless the mapping row under `SITE_SETTING` with the source code `CALCULATED_MEAN_PRESSURE` has the target 1. Its target is 0 in both conversions, so that by default the conversion records only what was measured, and a hospital that charts only 110/70 can switch the step on by changing that one row. The drug step takes only the actions that the mapping table lists as given, and a second drug step writes one row for each period that an infusion ran at one rate. Further steps write the ASA class, the anaesthesia events, and airways and lines. Every row of an anaesthetic's own record carries the anaesthetic's `visit_detail_id`, and a measurement or an observation also points at the anaesthetic's own procedure row through its event field, but only when it was taken from the anaesthetic's start to its end, with a margin either side. For an anaesthetic with no recorded stop, the window runs from the start, less the margin, with no upper end. The margin is 15 minutes, and it is set in one place: the target of the mapping row under `SITE_SETTING` with the source code `EVENT_LINK_MARGIN_MINUTES`, which each of those steps reads. A mapping row was chosen over a number written into each step because it is the only place that every step, the release script and the source drafts already read on both engines, so that changing the one row changes the link everywhere, and the hospital can change it without changing a step. The remaining steps write staff without their names, wards, operations for the cases that were carried out, diagnoses, deaths, and the one row that describes the database. Two derived steps then write the custom tables: `anaesthetic`, one row for each anaesthetic with the facts that most questions start from (its type, start, end, duration, the child's age in days and in completed years and months, the ASA class, the most recent weight and the provider), whose identifier is that of the anaesthetic's own procedure row; and `anaesthetic_phase`, one row for each phase of an anaesthetic, which for now is the whole anaesthetic, with the rule that defined it and the rule's version. A further phase is a further row. The custom tables hold no summary of the readings, so a question about blood pressure reads the raw measurements. The conversion for the real source is not part of this repository.

An anaesthetic with a start and no recorded stop is written. Its `visit_detail_end_datetime` is empty and its `visit_detail_end_date` is the date of its start, because CDM 5.4 requires an end date on VISIT_DETAIL; its own procedure row, its row in `anaesthetic` and its whole phase have an empty end, `duration_minutes` is empty, and the weight is the most recent one up to the start. An anaesthetic whose stop is before its start is still left out, and the run counts it.

The age follows clinical convention, which counts by calendar date: a child is one year old from the date of the first birthday, whatever the hour of birth. `age_years` and `age_months` count the whole years and months completed from the date of birth to the date of the start, by comparing the month and the day of the month, and never by the year boundaries that `DATEDIFF(year, ...)` counts. A year or a month is completed on the day of the month of birth, or on the first day of the next month where that month has no such day, so a child born on 29 February turns one on 1 March in a year without that date. `age_days` keeps the count of calendar days, which differs from the age in years by one day around a birthday in a leap year. A target query that asks about children under one year uses `age_years < 1`, or, on the CDM tables, the same rule written as a difference of dates in the form yyyymmdd that is less than 10000, so that both forms give the same answer. A blood pressure whose diastolic part is empty, as in 110/, gives a systolic row and no diastolic row, because the step treats an empty part as no value where SQL Server would otherwise read it as 0.

## Planted scenarios

The synthetic rows are realistic in their spread, but no row of them has a known answer. A planted scenario is a small set of source rows written by hand for one awkward case, each with the OMOP rows and query results that it must produce. A scenario is a folder under the conversion's `scenarios/`, and the conversion for the real source holds a twin of each, under the same name and with the same expectations, so that only the source names differ. The folder holds `scenario.json`, with a one-sentence description of the case and the list of expectations, and `rows.sql`, which holds plain `INSERT` statements into the source tables. Each expectation is one sentence, one T-SQL `SELECT` against `omop.<table>` and the one row it must give, which is a count or a few values.

Every identifier in `rows.sql` of nine or more digits lies between 990,000,000 and 990,999,999, apart from the source codes of the conversion's own mapping rows. The sandbox never generates a key in that range, because its keys are the row number or a million times the number of the key's group plus the row number, so a planted row cannot collide with a generated one and can be found again by its identifier. The runner refuses a `rows.sql` that holds anything but `INSERT INTO` a source table that the catalogue names, written in one part with its columns, followed by `VALUES` that are literals only. A scenario that needs many rows, such as a long anaesthetic with thousands of readings, may instead `SELECT` from rows of literals given inline and cross joined, computing with arithmetic, `CAST` and `DATEADD` alone, so that it still reads no table. No literal may hold a line break or `$(`, and no line of the file may be one that `sqlcmd` would read as a command. Each expectation must be one `SELECT` under the rules that the release script applies to a gate, and may read only the OMOP tables.

`convert.run` plants the rows after the sandbox is built and before the core layer runs, as rows of the source would arrive. After the steps and the gates it runs every expectation and reports each one as met or not met, and an expectation that is not met, or a scenario that could not be planted, is a failure of the run, so the command exits with 1. Two scenarios plant the cases of the neonatal question: `neonatal_mean_pressure_minutes` gives eight neonates readings that test how long a pressure below 40 stands, and deaths 30, 90 and 91 days after the date of the start, and `neonatal_mean_pressure_who_counts` tests which anaesthetics the question counts, with children aged 28 and 27 days, a charted pressure without a mean, a low mean that the source did not accept, and a neonate with two anaesthetics. Each expectation states the minutes below 40 and whether the child counts as having died, written by the rules of the query, and a test shows that each band of the query moves by exactly what the cases imply. By default every scenario of the folder is planted. `--scenarios` names those to plant, and `--no-scenarios` plants none. The gates must still pass with the scenarios planted. A scenario that exists to make a gate fail names that gate under `fails_gate` in `scenario.json`; it is left out of the default set and runs only when it is named, as a test does.

The SQL Server harness loads `clarity_shadow` with the sandbox's rows as they were before any scenario was planted, runs each scenario's `rows.sql` on SQL Server as written, and evaluates every expectation on the published schema once the release script has run, beside DuckDB's answer. With `--run`, the readiness statement of a target query ends with one sentence that says how many planted scenarios bear on the tables that the query reads, because one of their expectations reads such a table, and whether the run met their expectations.

## Quality gates and the release script

The steps of the core layer run first and the steps of the anaesthesia layer after them, as they would at a hospital, and the runner refuses a conversion that lists them in any other order. A core step therefore cannot lean on a row that the anaesthesia layer writes.

The anaesthesia layer keeps its identifiers in a range of its own. Each anaesthesia step numbers its rows from 1, in an order that the step makes complete with tie-breaks, so that the same rows always take the same numbers. The runner and the release script then add a base: the setting `identifier_offset`, 5,000,000,000 by default, for the first step that writes a table, and the highest identifier that the layer has already written to that table for each later step. The steps that write the anaesthetic itself, to VISIT_DETAIL and PROCEDURE_OCCURRENCE, give each anaesthetic one number, so that an anaesthetic listed twice repeats its identifier and the primary key refuses it. A reference from one anaesthesia row to another, such as `measurement_event_id`, is read back from the published view and so carries the final identifier. Core steps number their own rows, as the core would. Before the anaesthesia layer runs, the runner reports any table whose core rows already reach the offset, and any core table that lacks a field of CDM 5.4.

`run` takes a hook that is called between the two layers, so that a test can alter the stand-in core as a real core might differ from the guess the core steps make. The tests use it to show that a core which hashes `visit_source_value`, already holds visit details, lacks the fields that CDM 5.4 added, or keeps identifiers just below the limit of `INT` either works or fails a gate or reports a problem.

A conversion folder may hold `gates/`, with one `SELECT` in each file. A gate lists the rows that break a rule, so a gate that lists no rows has passed. The runner executes every gate after the steps and reports each one. Two gates fail when the layer has written nothing where it should have: one when no anaesthetic was written at all, and one, which reads the source table and is therefore specific to the site, when fewer than nine in ten of the source's anaesthetics that have a start, and no stop before it, became a visit detail. An empty end breaks no gate. Two more check the custom tables: `anaesthetic` must hold exactly one row for each anaesthetic and none for anything else, and each anaesthetic must have one whole-anaesthetic phase that starts and ends with it.

A conversion folder may also hold `counts/`, with one `SELECT` in each file that gives one row with one number, and never an identifier. The first line of the file is a comment that holds the sentence which reports the count, with `{count}` where the number goes. The invented conversion counts the anaesthetics that the layer leaves out because the stop is before the start, and those for which it found no hospital visit in the core, such as an anaesthetic without a theatre case or one of a test patient. The runner runs every count after the gates, reports each one in its report under `counts` and in the command's output, and fails a run in which a count cannot be run. A count does not fail a run by its number.

`core/schemalyser/release.py` writes the release script for the anaesthesia layer, to be run with `sqlcmd` after the core refresh:

    python -m schemalyser.release CONVERSION --catalogue CATALOGUE.csv --out FOLDER

The script keeps the anaesthesia rows in tables of their own, in a schema of their own, each with a primary key on its identifier and every identifier typed as `BIGINT` by default, whatever type the core uses. It publishes one view for each of those tables that joins the core's rows to them, and a view of the core's own rows for every other table of CDM 5.4, so that the published schema is a complete CDM that OHDSI WebAPI can use as a source. It creates the custom tables in the anaesthesia layer's own schema, runs the derived steps after the anaesthesia steps, and publishes a view of each custom table's rows in the published schema. It changes no core table. After the rows written to each table, it reports each of the conversion's counts as the sentence with its number in place. It carries the mapping rows inside itself, because a database cannot read a file from a repository; `release.script` can be given other rows to carry, as the SQL Server harness does with the rows derived from a vocabulary. The same command writes `source_manifest.csv`, the list of source tables and columns that the anaesthesia steps read, and it exits with 1 when it refuses anything.

The script runs its table definitions, the removal of its previous rows, the new rows and the gates inside one transaction. A table from an earlier run that no longer matches its definition, for example after a change of identifier type, is dropped and created again inside that transaction. The setting `on_failure` decides what a failed gate leaves behind. With `keep`, the default, the transaction rolls back and the previous run's rows stay in place. With `empty`, the removal is committed first, so a failed gate leaves the layer's tables empty; this suits a core that regenerates its surrogate keys at each refresh, where the previous rows would point at the wrong people.

What is assumed about the real database is held in settings and not in the steps: the schema of the core tables, the schema for the anaesthesia tables, the schema for the views, the prefix that reaches the source tables, the identifier type, the identifier offset and `on_failure`. A conversion folder may set them in `release.json`. Each setting is checked: a schema name must be a plain name, the three schemas must differ, the identifier type must be `INT` or `BIGINT` with room above the offset, and the source prefix must be one to three plain names, each followed by a full stop.

The four places are `sqlcmd` variables, and the operator gives each one with `-v`:

    sqlcmd -S SERVER -d DATABASE -b -i release.sql -v OmopSchemaName="dbo" AnaesSchemaName="anaes_cdm" AnaesPubSchemaName="anaes_pub" SourcePrefix="clarity_stage."

The script sets none of them itself, because a `:setvar` in a script overrides `-v`, as a test on the `sqlcmd` of SQL Server 2022 confirmed. If a variable has no value, `sqlcmd` stops before the script changes anything. The script begins with a batch of guards, which stop it before any change if a schema name given with `-v` is not a plain name, if two of the three schemas are the same, or if the core already holds an identifier at or above the offset in a table that the layer adds to.

Everything that the script carries from the conversion folder is checked first, because `sqlcmd` reads a script line by line and substitutes `$(name)` wherever it appears. A step or a gate must be exactly one `SELECT`, or a union of `SELECT`s, with no `INTO`, no variable, no table named in four parts, and none of `OPENQUERY`, `OPENROWSET`, `OPENDATASOURCE` or `EXEC`. Every output column of a step must be a field of its table, named once. `tables.json` is checked as strictly, so a hostile name or type, or a description that holds a line break or `$(`, is refused. No literal or identifier in a step or a gate, and no value of a mapping row, may hold a line break or `$(`, and a step or gate file name may hold only letters, digits, full stops, hyphens and underscores. The wording of the script's comments and messages is kept in `release.WORDING`.

## Profiling the core

The anaesthesia layer rests on guesses about a core that nobody here can see: its CDM version, the type and size of its identifiers, whether it populates VISIT_DETAIL, which type concepts it already loads, and above all whether its `*_source_value` fields hold the source system's keys as text, which every anaesthesia step joins on. `core/schemalyser/profile.py` writes one T-SQL script that the central team runs to test those guesses:

    python -m schemalyser.profile CONVERSION --out core_profile.sql [--source-prefix PREFIX] [--omop-schema SCHEMA]

The script follows the layout of the profiling scripts that the team already runs. It fills one global temporary table with header and data rows, in the columns `ITEM_CATEGORY` and `VALUE_01` to `VALUE_05`, and returns them as one result set to be saved as CSV. It reports the versions recorded in CDM_SOURCE; for each table of CDM 5.4, whether it exists, its rows rounded down to ten, the type of its primary key and the number of digits in the highest key; the CDM 5.4 fields that the core lacks and those whose type differs; the rows of each table that the layer adds to, counted by type concept; and whether every person has an observation period. For each join between a core source value field and a source column, which it finds in the step SQL with sqlglot, it reports how many values the core field holds, the share made only of digits and their range of lengths. Where the source tables can be reached through the source prefix, it also counts the distinct source keys and how many of them the core holds. That match rate is the most important figure in the profile. A join to a table that the layer itself writes, such as VISIT_DETAIL, finds the layer's own rows, so it is left out.

The script returns no row of data and no source value. Every name in it comes from the CDM field list, from the step SQL or from a setting, and the module refuses a setting or a name that is not a plain name. Each question runs through `sp_executesql` inside `TRY` and `CATCH`, so a missing table or field records an error row and the script carries on.

    python -m schemalyser.profile --read RESULT.csv CONVERSION

This reads the saved result, with or without a header line, and checks every row again: only the script's own categories, only names from the CDM field list or the conversion's own joins, and only whole numbers where counts belong. It then prints a summary that holds only standard names and rounded numbers, and the findings for the register of guesses, each with the setting or the step that it bears on. The reader also accepts the output of the team's general database profile and takes from it which CDM tables and fields exist, the identifier types and the approximate row counts. It counts local tables and fields without returning their names. `fixtures/profile/` holds the result of the script for the invented conversion as SQL Server returned it, the same script run against a schema that lacks most tables, and an invented general profile in the shape of CDM 5.3.

### The plain form of the core profile

The whole profile script stays as it is, for a central team that prefers one run, but the checklist no longer asks for it first. `profile.plain` gives the same questions as a short list of plain queries in two tiers, each one `SELECT` with no variable, dynamic SQL, setting, temporary table or error handling, returning rows in the profile's own layout so that `profile.read` accepts the result.

- **Tier one** is one query, `plain_tier_one`, that reads only SQL Server's own records (`sys.objects`, `sys.partitions` with `index_id IN (0, 1)`, `sys.columns` and `INFORMATION_SCHEMA`) for a literal list of the CDM tables and fields that are needed. It returns a `PROFILE` row, a `CDM_TABLE` row for every listed table, whether the core holds it or not, with its size rounded down to ten and the type of its key, and a `CDM_FIELD_ABSENT` or `CDM_FIELD_TYPE` row for each listed field that the core lacks or holds with another type. It reads no table.
- **Tier two** reads data, each query bounded by construction, and none is offered until tier one has given the size of its table. A table whose size the server keeps no record of, such as a view, gets only a count that says it reads the whole table. `plain_key` takes one `MAX` over a table's key and returns its number of digits. `plain_cdm_source` reads the versions. `plain_type_concepts` counts a table's rows by type concept, from `TABLESAMPLE SYSTEM (p PERCENT)` with the counts scaled up where the table is over `checks.PLAIN_EXACT_ROWS`. `plain_match` takes up to `PLAIN_KEY_SAMPLE` (10,000) distinct keys from the source table, through a literal sample of its pages where the check results show it to be large, and looks each up in the core field; it is used where the core table is no larger than the limit and the check results give the source table's size, so that its figures agree with the whole script's, and it never joins two whole tables. Where the core table is over the limit, `plain_match_core` measures the same join from the core side instead: it reads a literal share of the core table's pages, chosen from its known size so that the sample holds about 5,000,000 rows, takes up to 10,000 distinct non-empty values of the core field, and looks each one up as a key of the table that the source key refers to, found from a join that the requests or the conversion make to a column that keys its own table, or as the source column itself where there is none. A whole-number key is looked up through `TRY_CAST`, so that the lookup can use the key's index. Its result has a category of its own, `SOURCE_KEY_MATCH_SAMPLED`, which the whole script never writes and `profile.read` validates as it validates a match, with the values sampled, those found and the percentage under the same rounding and minimum. A match of a join from either side replaces the other side's, and on the checklist either settles the item: a share of 95 per cent or more confirms the guess, a lower one is a finding that it does not hold, and a figure from the core side is described as an estimate from a sample.

Every data table is read `WITH (NOLOCK)`, every count is rounded down to ten, and nothing returns a row of data or a source value. The plain form leaves out what cannot be had within these bounds: the count of local tables and local fields, which would need the whole CDM field list in the query; the shape of each source value field, which reads the whole field; the observation periods, which read the whole of PERSON and OBSERVATION_PERIOD; and a tier-one report on any field that is not needed. The match counts at most 10,000 sampled keys rather than every distinct key, so on a large source table it is an estimate. Each tier-two query that the checklist offers always returns one row, so a query that finds nothing is recorded; the count of type concepts can return no row, as the whole script's can, and is not offered on the checklist.

On the checklist, each open core item, and each item on a core source value field, carries the plain profile queries that would settle it, only for the tables, fields and joins of that target, under the same three columns as the checks. The queries appear on the page in a short section of their own, for the central OMOP team, tier one first, and one box takes their pasted results. `profile.pasted_rows` reads a results grid or a CSV file, `profile.accepted_rows` reads each row with `profile.read` and leaves out any row that it refuses, and `profile.merged` adds the rows to the core profile in hand: a table's row is merged value by value, so that the key from tier two joins the size from tier one; tier one's report on a table replaces the earlier fields of that table; and a match, the versions or a set of type concepts replaces the earlier one. The merged profile is read again as a whole, written into the state as `core-profile.csv`, and the checklist is worked out again; a button saves it for the state folder. An earlier general profile is not kept, because its rows cannot stand beside the core profile's. The match queries need `source_prefix` in `release.json`, and without it the item says so.

## The open questions

Every stage rests on something about the real hospital that the project cannot see for itself. `core/schemalyser/questions.py` lists each such question in one place, in `questions.csv`:

    python -m schemalyser.questions WORLD CONVERSION [--checks FILE] [--profile FILE] [--build] --out questions.csv

Each row gives the question as a statement of what is not yet known, what it decides, where the current answer comes from, exactly what evidence would settle it, who can supply that evidence, through which mechanism, how far it is answered, and the evidence in hand. The columns are `question_id`, `stage`, `question`, `decides`, `currently_from`, `evidence_needed`, `who`, `mechanism`, `status` and `evidence_in_hand`. The status is `answered`, `partly` or `open`. The people who act are the analytics team, the central OMOP team and the clinical lead, and the mechanisms are the catalogue export, the check script, the site rules, the mapping rows, the core profile script, the release settings and a decision. The current answer comes from an invented default, a public source, the site rules, the check results, the mapping rows, the core profile, the catalogue export, the release settings or a guess.

The register and all of its wording are fixed in the module, in one dictionary, so that the clinical lead can review them in one place. The statuses and the evidence in hand are computed from what the tool holds: the catalogue, the site rules, the check results if any, the conversion folder with its mapping rows, `derived_mappings.json` and `release.json`, the table of tunable parameters, and the result of the core profile script if any. The questions cover:

- for the analyser, the catalogue, each kind of thing in the requests that could not be read, and each kind of check, with how many are planned and how many the results answer;
- for the shadow database, each group of tunable parameters with the source that each one reports, the roles in the site rules that could not be used, and how many anaesthetics each child has. A duration within one table is settled by a spans check on the pair of columns that the roles name, a rate by the count that would give it, and anything else by the clinical lead under `tuning`. With `--build`, the sandbox is built and each role that it could not apply has a row of its own;
- for the core, its CDM version, each core field that the anaesthesia steps join on, each table that the layer adds to, VISIT_DETAIL and the observation periods;
- for the anaesthesia layer, each mapping vocabulary that its steps read, found in the step SQL, with the source column that it maps, whether the check results list that column's values, and how many listed values have no mapping row. A vocabulary is answered only when its values are listed and none is without a row;
- for the release, each setting in `release.py`, whether the core regenerates its surrogate keys at each refresh, and how the release will be run.

The evidence in hand holds only counts and names. A name comes from the catalogue, the site rules, the CDM field list, the conversion's own steps and settings, or the register. The module never writes a value from the check results, a setting's value or anything from the text of a request. `questions.summary` gives the counts by stage and status, and by who must act, for the end of a scorecard.

## One target query

The tool cannot discover by itself how the source database stores an anaesthetic. The conversion's steps are a hypothesis written from public knowledge, and the sample queries from the data team are the evidence for or against it. `core/schemalyser/target.py` ties the two to one target query, which is a single T-SQL `SELECT` against the OMOP tables written as `omop.<table>`, as the steps are:

    python -m schemalyser.target WORLD CONVERSION TARGET.sql [--checks FILE] [--profile FILE] [--run] --out FOLDER

The module refuses anything but one `SELECT` that reads only the tables of CDM 5.4 and the conversion's custom tables. It reports the fields that the query uses, through its aliases, and the concept ids that it compares each concept field with.

It then traces the query back through the conversion. A step is relevant when it writes a table that the query reads and can write rows that the query keeps. A step that does not write a field that a condition of the query needs is left out, because an empty field never meets the condition. Where the query compares a field with fixed values, such as concept ids, a step is kept when its expression for that field can give one of them, as a constant or as the target of a mapping row under a vocabulary that the step looks up. Where the field comes from a vocabulary whose rows are only proposed from labels, the tool cannot tell, so it keeps the step as possible and says so. The same test runs from each relevant step to the earlier steps that write an OMOP table it reads, so that the trace reaches the anaesthetic's visit detail and procedure row and the core's visits and people. Each step keeps its layer, and the core steps are the ones that the hospital's core must supply. A query that reads a custom table is traced through the derived step that writes it: a field that the derived step copies from an OMOP table can hold what the earlier steps that write that field can, and a concept that the query needs is credited to the step that writes it there. A table that the derived step brings in with a left join, and that feeds no field the query reads, is left out, so that a question that does not read an anaesthetic's weight does not rest on the steps that write weights.

The requirements come from the analyser itself. The relevant steps are passed through `convert.as_request` and read by `analyse_request`, so that each requirement is a finding in the same vocabulary as the evidence. The checklist, `checklist.csv`, has one row for each source table, column, join and filter that the steps rest on, each concept that the query needs, each further mapping vocabulary, the meaning of each value that the query reads, the tunable parameters that bear on the dates it uses, and each core field that the anaesthesia steps join on or that the query reads from a table only the core writes. Its columns are those of `questions.csv` with four more, `blocking`, `kind`, `intent` and `route`, and the rows for timing and for the core's source value fields are the register's own. A join is answered when at least one sample query makes the same join, in either direction and through a cast, and stays open when none does. A concept is open until a mapping row leads to it, and answered once the check results list a source code that has such a row.

An item blocks when, while it is open, the shadow database cannot simulate the query at all or cannot simulate it faithfully: a table or column that the catalogue does not list, an inner join that no sample query makes, a concept without a mapping row, a gating vocabulary without rows, and a core field that the query or an inner join depends on. Filters, meanings, durations and optional joins bear on realism and do not block. `readiness.txt` gives the steps by layer, the blocking items by status, who must act on each open one, and whether the shadow database is ready for the query, which it is when no blocking item is open.

The tool cannot write or repair the steps, because they are a hypothesis written from public knowledge. It can say what the hypothesis rests on and which parts of it the sample queries support, and three things help the data engineer to answer where the steps are wrong.

The first is the intent of each join. The author of the steps writes, once, what each join is meant to do, in `intents.json` in the conversion folder, so that the data engineer knows what is being asked even when the named join is wrong. Each entry names a join as a pair of columns, written `TABLE.COLUMN`, a filter as one column, or a mapping vocabulary, with the intent as one plain sentence: `{"join": ["ANAES_RECORD.VISIT_KEY", "VISIT.VISIT_KEY"], "intent": "This join finds the hospital visit that the anaesthetic took place in."}`. The file is checked like every other input: an intent is one line of at most 300 characters that begins with a capital letter and ends with a full stop, with no line break, no `$(`, no question and no exclamation, and each table, column and vocabulary must be one that the steps, their alternatives or the mapping rows name. A file that breaks a rule stops the checklist. The intent is given in the checklist's `intent` column for each join, filter and vocabulary that has one. A test fails when a join that a step of the invented conversion makes has no intent, and `target.joins_made` lists those joins for any conversion.

The second is the route that the sample queries take. For a join that no sample query makes, the tool searches the joins that the sample queries do make, as a graph with a table at each node and an edge for each pair of columns that some request joins, counted by the requests that join it. It looks for the shortest route between the same two tables, of at most three joins, and among routes of one length it prefers the one whose weakest join more requests make. The best route is given in the item's evidence, as in "The sample queries reach VISIT from ANAES_RECORD through THEATRE_CASE, by ANAES_RECORD.CASE_KEY = THEATRE_CASE.CASE_KEY (6 queries) and THEATRE_CASE.VISIT_KEY = VISIT.VISIT_KEY (1 query)", and in the `route` column as the joins separated by semicolons, each with its count of requests. Where there is no route, the evidence says that the sample queries do not connect the two tables at all, and how many request files the analyser could not read in full, because the evidence may lie in a part that it could not read. Every name comes from the analyser's findings, and so from the catalogue.

The third is an alternative. A step's entry in `conversion.json` may list `alternatives`, other single-`SELECT` files that make the same rows by another route, each a file name or an entry with a file and, if given, the step's own table and layer. They are checked with the layers, and the release script checks each as strictly as a step, although it carries only the step's own file. For each relevant step that offers alternatives, the checklist finds the joins that the step makes and those that each alternative would make in its place, and counts how many of them the sample queries make. The version with the fewest inner joins that no sample query makes, and then the largest share of joins that they make, is the best supported, and the evidence of each open join that the step makes and the readiness both say so, as in "The sample queries make 3 of the 4 joins that visit_detail_through_case.sql makes as written." The tool switches by itself in one case only, set out in the next paragraph; otherwise a person makes an alternative the step by editing `conversion.json`. `convert.run` ignores the alternatives, unless it is given `alternatives`, or the command `--alternative FILE`, to run a named alternative in its step's place so that it can be tested first.

The readiness ends with one sentence for each open blocking join for which there is something to do: if a better supported alternative does not make the join, the clinical lead can make that alternative the step, and otherwise, if the sample queries reach the same table by a route, the clinical lead can change the step to follow it. With `--run`, the sentence on the planted scenarios follows.

Once a catalogue is to hand, `routes.py` checks each step that offers alternatives against it. A step that reads a table or a column that the catalogue does not hold gives way to the first of its alternatives whose tables and columns the catalogue all holds; a step whose own names are all there is kept, and so is a step for which no alternative fits. An alternative may be given as `{"file": ..., "effect": ...}`, where `effect` is one sentence by the author of the conversion that says what the route changes in the answer, such as a group of patients that it can no longer leave out. The boundary applies the choice to its own copy of the state, so that the register, the checklist, the specification and the source query all follow the same route, and records it in `routes.json` in that copy. The checklist gains an item for each step that gave way, which says in one sentence which file it uses in place of which, because the catalogue does not hold which names; the item is answered, or partly answered where the alternative names an effect, for the clinical lead to accept. The same sentences appear at the head of the target's checklist on the page and in its readiness statement. An alternative that reads what the catalogue does not hold is left out when the checklist weighs a step's versions against the sample queries. A table or column that a step reads and the catalogue does not hold is an item that asks the person who keeps the conversion for a decision about the step, and never for evidence that the name exists. `core/tests/test_routes.py` tests this on the invented conversion, with `fixtures/routes/person_all_people.sql` as an alternative that cannot leave out test people.

`fixtures/conversion/` has followed that evidence. Its visit detail step, `visit_detail_through_case.sql`, reaches the anaesthetic's hospital visit through its theatre case, as the sample queries do, and its blood pressure step, `measurement_blood_pressure_through_anaesthetic.sql`, gives each reading the visit of its anaesthetic's visit detail. The former steps, `visit_detail.sql` and `measurement_blood_pressure.sql`, are now their alternatives, and the two joins that no sample query made are no longer needed. An anaesthetic without a theatre case is therefore left out, and the run counts it. Every planted anaesthetic has a theatre case as well as a visit key, so that each scenario is a complete record whichever route a step takes, and the scenario `anaesthetic_without_theatre_case` gives one anaesthetic none. Run with the former steps as alternatives, the conversion passes its gates and gives the same anaesthetics and the same answer to the infant query on the generated rows.

With `--run`, the module runs the conversion over the sandbox, runs the query on the synthetic rows with `translate.to_duckdb`, and writes `result.csv`. It also writes `published.sql`, the query with every table read from the release's published schema through the `$(AnaesPubSchemaName)` variable, for SQL Server. The same rules on names apply as for the register: the output holds only names from the catalogue, the site rules, the CDM field list, the conversion's own files and vocabularies, and the fixed wording, with the concept ids that the target query names. `fixtures/targets/` holds four target queries for the invented world, two of which ask the same question of the CDM tables and of the custom table `anaesthetic`. The fourth, `neonatal_low_mean_pressure.sql`, asks how many minutes of each neonatal anaesthetic were spent with a mean pressure below 40 and how many of the children died within 90 days. It is written with common table expressions, `ROW_NUMBER`, `LEAD` and `DATEDIFF`, and its header states each of its rules: a neonate is younger than 28 days by `age_days`; it reads the cuff mean and the arterial mean and not the calculated mean; it keeps the arterial reading where both have the same time; each reading stands until the next, or until the end for the last, for no longer than five minutes, and the last reading of an anaesthetic with no recorded end stands for no time; and it gives one row for each band of minutes, counting anaesthetics rather than children.

With `--draft`, or through `target.source_draft`, the module writes `source_draft.sql`, the same question as one T-SQL query that reads only the source tables, for the analytics team to read, correct and later run on the real database as the benchmark that the OMOP query must match. The query composes the relevant steps in the conversion's order as common table expressions, each with the step's own comment. A target query's own common table expressions follow them, renamed, and a column of the question is traced through them to the source columns behind it, so that the question's own lines carry only the assumptions about the concepts it compares with. Each OMOP table that a step reads becomes the union of the relevant steps before it that write that table, and the mapping rows become a table of values. An anaesthesia step's identifiers are moved past the layer's offset as the runner moves them, and the identifiers need only agree within the query. Each assumption the query rests on is numbered in its header and marked on the line it affects: each join between source columns, each code that a filter compares a source column with, each choice of the first row of a group, and each mapping row. On the synthetic data the draft gives the same answer as the OMOP query. The draft names the source tables and columns and carries the mapping rows with their local codes, so it is for use inside the hospital only; its first line says so, as do the help for `--draft` and the docstring of `target.source_draft`.

## The data dictionary and the review of a target query

Target queries may be written with the help of an LLM, which sees only the clinical question, the schema, the synthetic database and a data dictionary of the conversion. `core/schemalyser/dictionary.py` writes that dictionary from the conversion folder alone, with the names of the concepts taken from an Athena download when one is given:

    python -m schemalyser.dictionary CONVERSION [--vocabulary FOLDER] --out FOLDER

It writes `dictionary.json`, which the review reads, and `dictionary.md`, for a person or an LLM to read. It covers every table that the anaesthesia and derived layers write, and person, visit_occurrence and death, which a query joins to and which the core stand-in writes. For each field it gives how each step fills it, found in the step SQL with sqlglot: a fixed value, a value copied from the source, a concept that the mapping rows under a vocabulary give, the value of a field of another OMOP table, a value computed from others, or a choice among these. For a concept field it lists the concepts the field can hold, from the steps' constants and the target concepts of the mapping rows, following a field copied from another OMOP table back to the steps that can write the rows it reads. A field whose concepts come from a vocabulary proposed from labels, or from the source, is marked as open. For each value field it gives the units by concept, pairing a concept with its unit through the mapping rows of the same source code. It gives the fields that hold the identifier of an anaesthetic, which are those that hold the same identifier as a custom table's primary key or the visit detail's, and the conventions that the steps show, such as the concept 0 for a value without a mapping row, the rows that a gating vocabulary keeps, an empty end for a device still in place or an anaesthetic without a recorded stop, and the window, with its margin from the mapping row, within which a row points at its anaesthetic through its event field. For a custom table it gives each field's rule from `tables.json`.

The dictionary holds only names of OMOP and custom tables and fields, concept numbers and the attributes of concepts from the vocabulary, the names of mapping vocabularies, step file names, the descriptions in `tables.json`, text that a step itself writes as the value of a column, and its fixed wording. It never holds a source table or column name, a source code, a mapping row's description, a check result or a step's comment. The module checks its own output for the source names, text codes and descriptions that the conversion holds, and refuses to write a dictionary that holds one. A text that a step writes as a fixed value, such as the procedure_source_value of the anaesthetic's own row, is the conversion's own wording and is kept, even where the conversion also looks it up under a vocabulary of its own.

`target.review(query, dictionary)` checks a target query against the dictionary and returns its findings, each one sentence: a concept compared with a field in which the conversion never writes it, or writes it only in another field; a measurement or an observation related to an anaesthetic by anything but the documented links; a value field compared with a number where the rows that the query keeps hold more than one unit and the query does not restrict the unit; a table or field that the conversion does not write; and a field of a custom table that `tables.json` does not define. An empty list means only that nothing was found, not that the query is right. `python -m schemalyser.target ... --review` builds the dictionary from the conversion, writes the findings to `review.txt` and prints them.

## Running at the boundary

Whatever reads confidential input runs at the boundary: the analyser, which reads the data team's requests and the catalogue, the check script, the register of open questions and the checklist for each target query. Everything else, which is the stand-in database, the conversion run, the release script and the runs on SQL Server and ATLAS, works on synthetic data and stays as separate commands. Until now the boundary has been the page, offline. It can now also be a container with no network, run on each commit to the owner's private state repository, beside a second private repository that holds the analytics team's requests and is only read.

`core/schemalyser/boundary.py` does everything that the boundary does in one command, from two folders into one:

    python -m schemalyser.boundary --state STATE --requests REQUESTS --out OUT [--state-commit SHA] [--requests-commit SHA]

The state folder holds `catalogue.csv`, which is required, and may hold `site-rules.json`, `checks.csv`, a conversion folder named `conversion/`, target queries as `targets/*.sql`, the result of the core profile script as `core-profile.csv`, the facts that a person confirmed as `facts.json`, what the team's SQL showed in earlier runs as `sql_evidence.json`, and `boundary.json`. The last of these sets options, which for now are `includeSpans` and `includeFanout`. Both are true by default, and either can be set to false to leave those checks out of the script. The requests folder is any tree of `.sql` files, such as a checkout of the analytics team's repository. A request file that is a link, or larger than 2 MB, is left out and counted, and the `.git` folder is passed over.

The output folder must be empty or new. It receives the inventory pack in `inventory/`, built from the requests alone and without the check results, so that it holds no checked value; the whole check script, planned from the requests with the conversion added as one more request, as `convert.run` and the register plan it, so that each source column that a step maps has its values listed; `questions.csv` with `questions-summary.txt`; and for each target query a folder with `checklist.csv`, `readiness.txt` and `queries.sql`, the plain queries that its checklist offers now. The checklist plans its queries in the same way, from the requests and the whole conversion. The register and the checklists need a conversion, and without one the command writes the pack and the script and says what it has left out. `summary.md` is the page that a person reads first, on GitHub: what was read and what could not be read, as counts; the counts of questions by status and by who must act; and for each target query whether the shadow database is ready for it, with its open blocking items. `provenance.json` names the two commits, which must be hexadecimal, the options, a checksum of the Schemalyser code that ran, and a checksum of every other output. The output folder also receives `sql_evidence.json`, described below, for the state folder. Two runs over the same inputs on the same day give identical files. The wording that a person reads is kept in `boundary.WORDING`.

The command exits with 0 when it has written everything, with 1 when a target query could not be read, in which case everything else is still written and the summary names the query, and with 2 when the state folder, the requests folder, the output folder or a commit cannot be used, in which case nothing is written. A missing catalogue, site rules or options that are not valid JSON, check results or a profile in the wrong layout, and a conversion whose `conversion.json` cannot be read all make the state folder unusable. A target query that is not yet ready is not an error. Any other error ends the command with 3 and one fixed sentence, which carries no text from any input, because the text of an error could quote a request.

The boundary never builds the sandbox, never runs a conversion, never needs the vocabulary and never opens a network connection. It imports only the analyser's own modules at the top. The register and the checklists bring in duckdb, because `harness.py` and `convert.py` import it at the top of their modules, so the image installs it, although the boundary never calls it.

`tools/container/` holds the image. It is built on the official Python slim image, pinned by digest, installs sqlglot and duckdb from wheels whose checksums are given, removes pip, copies only `core/schemalyser`, and runs as a user who does not own the code, with the command as its entrypoint:

    docker build -f tools/container/Dockerfile -t schemalyser-boundary:dev .
    docker run --rm --network none --read-only --tmpfs /tmp -v STATE:/state:ro -v REQUESTS:/requests:ro -v OUT:/out schemalyser-boundary:dev

Run in this way, the container has no network apart from loopback, cannot change its inputs or its own files, and can leave its results only in the output folder. The outputs keep the same rule as every other output: every name comes from the catalogue, the site rules, the OMOP field list, the conversion's own files and vocabularies, the names of the target queries or the fixed wording, and nothing comes from the text of a request or from the values in the check results. The run does not decide what may be committed: a person reads the outputs and commits them to the state repository. The check script and the checklists name the hospital's tables and columns, so they belong only in its private repositories. The image is only as trustworthy as its build, so the hospital should build it from a reviewed commit, or pull it by a digest that it has checked. `tools/container/example-workflow.yml` is an example, not yet run, of a GitHub Actions workflow that does this on each commit and keeps the outputs as an artefact, without committing anything.

### The boundary on the page

The page runs the same code. Besides the separate choosers for the catalogue, the site rules and the check results, it takes a state folder in the layout above, or fetches the same files from Schemalyser's repository on GitHub. A file chosen on its own takes the place of the same file in the state folder, and both take the place of a fetched one. Once it has built the inventory, the worker writes the state and the requests into Pyodide's file system, which exists only in the worker's memory, and calls `boundary.produce` through `browser.boundary_run`, so that the page and the container cannot disagree. DuckDB is already loaded for the sandbox, so nothing more is fetched. The package that the page serves holds every file of `core/schemalyser`, as the container does, so `provenance.json` names the same fingerprint of the code. The commits are given only when every file of the state, or every request, came from the fetch.

The page shows a checklist for each target query: its readiness, the number of its blocking items that are answered, and its items under a mark that shows the computed status, which cannot be changed by hand. The open items that a sample query could settle come first: a table or column that no sample query uses, a join that none makes, and a filter that none applies. The open items that need the check results, the mapping rows, the site rules or the core profile follow, each with who must act and how, in the readiness statement's own words, and the answered items are folded away. Each item shows the checklist's own `evidence_needed` and `evidence_in_hand`. An open item with a query shows its state, its reason and the query in a block with a button that copies it, and the table sizes query has a short section of its own at the head of the checklist. One box above the checklists takes pasted results. The worker reads them through `browser.checks_paste`, which uses `Checks.from_pasted` and `Checks.merged`, writes the merged results into the state as `checks.csv`, and runs the boundary again over the same state and requests, so that the items tick and the next queries appear without starting over; the page builds and changes no SQL itself. The pasted results are kept until the page is cleared, so that a new analysis keeps them, and once anything has been pasted the provenance names no state commit. A button saves the merged results as `checks.csv` for the state folder, and the download and the whole check script follow them. The data engineer can add request files after an analysis and analyse again without choosing anything else; the earlier requests are kept, and the page marks each item that the new files answered and gives the new count. When the network returns, the page locks as before, and it keeps only the checklist's identifiers and statuses, which hold the same names as the download, so that a new analysis, after fetching again, can show what changed. The download holds the inventory as before and, in a folder named `boundary`, every file that the boundary command writes. Without a conversion and target queries the page says what to supply to see a checklist. The page offers the specification and the audit query only once the question is ready to be answered from the source database, so that nobody writes or runs the audit query on an item that is still open or that a person has said is wrong.

Before any file is chosen, a button loads an invented example that is served with the page: the invented world's catalogue, site rules, check results, conversion, target queries and requests, copied from `fixtures/` into `public/example/` by `scripts/prepare_assets.py`, with a list of them in `manifest.json`. It is fetched from the site while the page is online. The page marks it as invented in the third step and above the checklist, and choosing any file of one's own discards it, clears the worker and starts clean.

## Answering from the source database first

A first audit is answered from the source database by the analytics team alone, and the OMOP release follows as a second phase. The source draft of a target query answers the same question from the source tables, and needs no core, no release and no operator, so each checklist item now says, in the column `phase`, which phase needs it: `source`, where the source draft rests on it (a table, a column, a join or a filter that the analyser finds in the draft, a vocabulary or a concept whose mapping rows the draft carries, or a step that the draft may include), or `release`, for everything else, which is the core's items, the source keys that the core holds, and the meaning and timing that make the shadow database realistic. The readiness ends with one sentence for each phase: whether the question is ready to be answered from the source database, counting only the source phase's blocking items, and whether it is ready for the OMOP release, counting them all.

The page leads each checklist with the source phase: its tally, its verdict, its queries and its items. Everything that only the release needs, including the core profile's queries for the central OMOP team, is folded under one heading for the later OMOP release and is not counted in the tally. Once the source phase is ready, the page offers the audit query, which is the source draft, with buttons that copy and save it, under a sentence that says that it is the question itself, to be run once on the source database. The page names the tables that it reads with their known sizes, says that it is the one query that reads the large tables through its own joins, so that its cost depends on the indexes, and says whether it returns only counts, where every output column of its last SELECT is an aggregate or a grouping expression, or a row for each record, in which case its result belongs under the audit's own approval. The draft reads each source table `WITH (NOLOCK)`, which DuckDB's translation drops, and it gives the same answers as before on both engines. The draft names source tables and holds local codes, so the page, which runs inside the hospital, offers it, the boundary writes it as `targets/NAME/source_draft.sql` only when `boundary.json` sets `writeSourceDraft`, and it is never part of the inventory pack.

### What an answer depends on

`target.answer_dependencies` follows each output column and each condition of a target query back through the steps by column lineage, and gives the source tables, columns, joins, filters, mapping vocabularies and steps that the answer depends on. Within a step, the needed outputs, every WHERE, HAVING, GROUP BY and window, and every inner join's condition count; a left join counts only where a counted expression reads one of its columns, and a column of a common table expression or a derived table counts the expression that its SELECT gives it. A left join that nothing counted reads is reported as not needed for the answer, provided that it does not multiply rows. The checklist uses this, and not the whole source draft, to say which phase needs an item: an item that the answer does not depend on has the phase `unneeded`, stays visible under its own heading, and does not block answering from the source database, although the release still needs it. For the neonatal question this takes out the provider's codes, the ward or department join and the visit detail's code on both worlds. The rule is conservative where it cannot tell: a window or a WHERE inside a derived table counts even where the table is left joined.

### Questions before queries

A person's answer counts. The state may hold `facts.json`, read by `facts.py`: each fact has a kind (a join, these two columns do join, yes or no, with the columns that do join where the answer is no; a filter, the steps' comparison of a column with fixed values is right, yes or no; or codes, the local codes under a mapping vocabulary that mean a concept), the catalogue names it is about, the answer and the date, and optionally who gave it. Every name must resolve in the catalogue, and a code must pass the rule for a value in the check results. Who gave a fact stays in `facts.json` and is never written to any other output; the checklist says that a person confirmed it, and on which date. A "yes" settles a join, a filter or a codes item as existing SQL or a check result does, and a "no" keeps it open and says which step must change, and what it should join on where the person named the columns. The codes of a codes fact become mapping rows in `site_mappings.csv` in the conversion folder, which `convert.mapping_dicts` loads beside `source_to_concept_map.csv` for the conversion runner, the checklist, the register, the release script and the dictionary, so that nobody edits a mapping file by hand; where both give a row for the same code under the same vocabulary, the site's row wins, because it records what a person at the site confirmed.

Each open item of the first phase that a person can settle puts the question first, in one plain sentence that a colleague can answer from knowledge, with controls that record the answer through `browser.fact_add`, and offers its query second, as the alternative. A section at the head of the first phase gathers the questions into one list with a copy button, to send to a colleague. The save button includes `facts.json` and the site's mapping rows.

What the team's SQL showed is kept in the state as well, so that it still counts once the request files are no longer to hand. Each run writes `sql_evidence.json`, read and written by `sql_evidence.py`: for each table and column that a request file uses, each pair of columns that one joins and each column that one compares with fixed values, the catalogue names, the number of request files that showed it and the date of the run, and nothing else, so it holds no text of any request and no file name. A finding that an earlier run saw and the present files do not show is kept with its own count and date. On the way in, every name must resolve in the catalogue, each count must be a whole number of at least one and each date must be yyyy-mm-dd, and a file that breaks any of these is refused as a whole, as `facts.json` is. A saved finding settles its table, column, join or filter item as the SQL did, and the item says that Schemalyser saw it in so many of the team's queries on that date; where the present request files show the same finding, the item cites them instead. The page's button that saves the state includes the file, and a state folder chosen on the page may hold it and `facts.json`, so that the page can analyse such a state with target queries even when no request files are chosen. The fetch from GitHub does not yet take either file.

### A specification, and a check of a hand-written query

`target.specification` writes one page for a person who writes the audit query himself: the question and its rules, from the target's header comment; the tables, columns, joins and filters that the answer depends on, each marked as confirmed by existing SQL, by a person, by a check result, or not yet confirmed, with the left joins that the answer does not need; the local codes that lead to the concepts that the question compares with; the shape of the result; the rule for small numbers; and the planted cases that bear on the question, each with what its expectations say. It names source tables and local codes, so the page offers it, the boundary writes it only when `boundary.json` sets `writeSpecification`, and it is never in the inventory pack. `target.check_query`, and `python -m schemalyser.target ... --check-query FILE`, run a query written by hand over the source tables on the synthetic database, with the planted cases, beside the target's own answer on the same rows, and report whether the two tables agree, showing both and the rows that differ. It compares answers before any blanking and accepts a hand-written query that blanks small counts. Nothing of the hand-written query is written to an output. The page describes the command, because building the synthetic database and running the conversion in the browser would take too long. The first phase on the page ends with the specification, the check, and last, as a reference, the generated query, with the warning that it builds every row of the steps before it keeps the question's rows and is not suitable to run on a large database until it has been restructured.

### The source query, restructured to start from the cohort

`target.source_query` gives the question as one query over the source tables in a form fit to run on a large database. It takes the composition of `target.source_draft` and rewrites it in `restructure.py`, one checked rewrite at a time: a surrogate number that a step makes with DENSE_RANK over one key is replaced by the key itself, with the layer's constant offset, where one step writes the table; a join on a key cast to text becomes a join on the raw key, where the catalogue gives both sides the same kind, whole number or text; a number that the question only tests for being present becomes 1; columns, common table expressions and LEFT JOINs that nothing reads are dropped, a LEFT JOIN only where it is shown to give at most one row (a lookup of mapping rows with unique codes, a derived table filtered to the first row of each key, or a table whose key is the first column of one source table that the catalogue says may not be empty), and otherwise kept with a comment; and the question's conditions are pushed into the step that writes the table that they test, where that table is read only there: a concept becomes a condition on the local codes that map to it, written on the key itself where that is safe so that its index can be used, and a join to the question's cohort becomes a condition that the column is among the cohort's values. The common table expressions are then ordered so that each follows what it reads, so that the cohort comes first. The result is accepted only where no DENSE_RANK remains and every ROW_NUMBER either numbers within a key or lies in a step that the question's conditions restrict; otherwise the query is the composition as it was, with a header that says why and that it is not suitable for a large database. The assumptions in the header are cut down to those whose number still marks a line of the query. All four invented target queries and the realistic conversion's are restructured, and the tests and the SQL Server harness confirm, with the planted scenarios in place, that each gives exactly the answer of the composition and of the OMOP query. The page offers a restructured query as one that may be run, after the specification, and the composition only as a reference with its warning.

### The names of the concepts

A conversion folder may hold `concept_names.csv`, the vocabulary's own name for each concept that its steps write as a constant, that its mapping rows lead to, or that a target query compares with. `python -m schemalyser.concepts CONVERSION --vocabulary ATHENA --targets FOLDER` writes it from an Athena download, and a test confirms that the invented conversion's file is what the download gives. Wherever a person is asked about a concept or shown one, in the questions, the items and the specification, the concept appears as its name with its number in brackets, for example "Invasive Mean blood pressure (concept 21490852)", and as "the concept N" where the file gives no name.

### A result that is safe by default

The generated query and the specification end with an outer SELECT that leaves blank any count from 1 to 4, with a comment that it may be removed where the audit's approval allows exact small numbers. `target.count_columns` works out which output columns are counts from the query itself: a COUNT, or a SUM of an indicator that is only 0 or 1, looking through COALESCE and through a column of a common table expression to its CASE. The neonatal target counts children as well as anaesthetics. With `advice`, `target.review` adds two findings that advise and do not block: the query counts records where it could also count people, and the query returns a row for each record.

### Honest words, and the sample

Each plain query says that WITH (NOLOCK) takes no row locks but holds a schema lock while it runs, so that it should not run during the nightly load, and a sampled query says that its counts are estimates scaled up from a sample of about five million rows. The percentage is a fraction where it must be, so that the sample is about five million rows at any size of table, and every sample carries the same literal `REPEATABLE` seed, so that the guard and the main query read the same pages; the `sampled` row records the percentage rounded to a whole number of at least one. `docs/first-ask-note.md`, which the page shows with a button that copies it, is the note to send with the first ask.

### A meeting with a colleague

The page is written for a clinician and a colleague who writes SQL, at one computer. The first screen says what the page is for in plain words and folds away what a meeting does not need: the full catalogue query, the steps for taking the tab offline, the page's checks on itself (including the two refusals that the worker's check of the policy leaves in the console), and the fetch from GitHub, which a link with `?source=github` opens at once. The head of each checklist says what Schemalyser still needs, as questions for the colleague and short queries, and the items that need him come first; the rest, and each item's own account, are folded beneath. No step's file name is shown on an item: a route is described by the tables it reads.

After the first query, a table or column that the audit needs and that did not come back is described as not visible to this login, because `INFORMATION_SCHEMA` shows only what a login may see. The route chosen in its place is provisional, and the item asks whether the name does not exist, exists but cannot be seen, or is not known (a fact of the kind `route`).

Every question has three answers. A join question states what the match is for, which side has one row and which may have many, from whether each column is its own table's key by its name and place, and says so where one step matches the same column to two tables for different rows. A filter question asks what a value marks. "Not sure" is a fact with the answer `unsure`, so the question is not asked again; for a join, the item then offers a match query (`Check.matched_plain`), which takes up to 10,000 distinct values of the column on the many side and counts how many have a row on the other, returning only counts, and a share of 95 per cent or more settles the join. A "no" that names the columns that do match is acted on at the boundary: `routes.rejoin` changes, in the copy of the steps, each step that matches the two tables on the old pair to match them on the new pair, and the item for the new pair is answered; where no step can be changed so, the item says that the clinician will change it after the meeting. A list of columns to choose from holds only columns that could be keys, and never a person's descriptive columns.

Codes are found by a name search, never from memory. Where the site rules give a definition table for the coded column, the item offers one query on that table alone, for the codes and names whose name holds any of the search words that `concept_words.csv` in the conversion gives for each concept, with the concept's meaning in plain words. The colleague pastes the result; the page lists the candidates, and the two people choose what each is, expecting several rows for one meaning; the choices become codes facts. The names are shown only on the page and are written into no file. In the first phase no counting or sampled query on a large table is offered for codes. Where the sizes are not visible to the login, a count is offered only for a definition table, which is small by its role.

Each checklist ends by saying what is settled, what remains and who can settle each part, with a button that saves the state and a sentence saying where to keep it, and the specification is offered whatever remains, with each open point as an unsettled assumption. The reference query is offered once nothing remains, as a reference for the person who writes the audit query, and the page says once what should happen before any such query runs on a large database.

The specification is written in the hospital's own terms: the question from the target's header; the study period and the kinds of anaesthetic; where each part of the question comes from among the source tables on the routes in use; how the tables are joined and what confirmed each join; every row that the steps leave out, with the condition in source columns; the local codes with their meanings; the shape of the result; what is not yet settled; and the prepared cases that bear on the question. It names no field of the shared model. The study period and the kinds are kept in the state as `audit.json` (`target.read_settings`), entered on the page, and applied by `target.with_settings` to the target query's anaesthetic before anything else reads it, so that the specification and the reference query carry them; without them the target query is unchanged.

### The first ask, without a catalogue

A project can start without a catalogue export. With no catalogue, the page reads the chosen request files and the conversion's steps only to list the tables that they read in FROM and JOIN, and `first_ask.query` writes one query: for a literal list of those names, every column of each table that exists, in the nine fields of the catalogue query, with the size of the table from `sys.partitions`, rounded down to ten. It reads only the server's own records. The pasted result is read by `first_ask.read` as the catalogue, under the catalogue's own rules, and as `rows` check results, under theirs, and the analysis then runs as it does with a catalogue file. The sizes are already known, so the checklist asks for no table sizes query for those tables. A table whose size comes back empty, as for a view or where the account cannot read the server's own records, is recorded at once as having no recorded size, so that the table sizes query is not asked for it, and a query that needs its size counts it only up to 10,000,010 rows (`Check.plain(bounded=True)`): a count past 10,000,000 comes back as a skipped rows check with the reason `size`, and the checklist then offers no query that reads that table, because a view cannot be read in part with `TABLESAMPLE`. A button saves the catalogue, the merged check results and the core profile as one zip, so that a second project starts from them and is asked only for what is new. A catalogue file, the state folder and the fetch from GitHub work as before.

This is the one deliberate exception to the rule that no string from a request reaches an output, and it is contained tightly. The parser reads comments and strings as such, so nothing in them becomes a name; temporary tables, table variables, common table expressions and aliases are left out; a name is used only if it is a plain name by the catalogue's rule, of at most 128 characters; and at most `MAXIMUM_NAMES` (500) names are used, those that the most files read, with ties in alphabetical order, and the page says how many it left out, which a second project can ask about. The query is shown on the page, for the person who already holds the SQL, and it is never written into the inventory pack, the boundary's outputs, the provenance or any saved file, other than by the user's own copy. Once its result is pasted, every later output takes its names from that result. The tests confirm that a patient's name used as a temporary table, a common table expression, an alias, a string or a comment, and a name with a bracket, a quote, a semicolon, a line break or more than 128 characters, cannot reach the query, and that a plain table name does.

## Tests

- The core is tested with pytest against the invented fixtures.
- The built page is tested in a real browser with Playwright. The test loads the page, confirms that the worker cannot reach another site, takes the browser offline, analyses the invented requests, checks the download, and brings the network back to confirm that the page ends the worker and removes the list of files. Further tests run the boundary command over the invented world and confirm that the page's checklists, from a state folder or from GitHub, give the same counts and the same files, and that adding one request answers the join it makes.
- The plain queries are tested in DuckDB against the script's exact form, through `fixtures/answer_queries.py`, which answers them from the invented stand-in database and answers the table sizes query by counting. The page test pastes those answers and confirms that the items tick.
- A planted-values test runs the core over the invented requests and fails if any planted name, record number or date appears in any output.
- An allowlist test fails if any token in the pack is absent from the catalogue, the checks file, the site rules file or the fixed vocabulary.
- A vocabulary test fails if any fixture uses a table or column name outside the invented catalogue.

## Roles, maps and the standard counts (a prototype)

Until now the tool's knowledge of a hospital's database has lived in conversion steps that name particular tables, written separately for each world. This prototype tries another arrangement, in which an audit is written once against a description of an anaesthetic record and a small map supplies that description at each hospital. It sits beside the conversion and changes nothing in it. `core/schemalyser/rolemap.py` holds the code, and `core/schemalyser/rolemodel/` holds the data.

**The roles.** `rolemodel/contract.json` describes three role views with fixed columns, their types and their meanings, with no hospital in mind: `role_patient` (patient_key, birth_date, death_date, is_test), `role_anaesthetic` (anaesthetic_key, patient_key, start_time, stop_time) and `role_reading` (anaesthetic_key, kind, reading_time, value, accepted). The kind of a reading is `map_arterial` or `map_cuff` for a mean arterial pressure, and `other` for any other value in the anaesthetic's record. The views keep what an audit leaves out, such as test patients, anaesthetics with no stop and values that were not accepted, so that the counts can see them.

**The audit.** `rolemodel/neonatal_low_mean_pressure.sql` is the neonatal question as one SELECT over the role views. Its rules are those of the OMOP target query of the same name, with one difference that the role views force: where two readings of the same kind share a time, the audit keeps the lower value, because the views carry no order of entry. Its common table expression `banded` gives each anaesthetic's band and year, which the result uses below.

**The map.** A map is a folder with one SQL file for each role view and `map.json`. Each view is a single SELECT over the hospital's own tables, in T-SQL, that gives exactly the contract's columns in order and joins on the source's own keys. `rolemap.read_map` checks it as strictly as a step: one SELECT by the release script's rule, no WITH of its own, no role view read, every column named with its table's alias, and every table and column in the catalogue. `map.json` gives evidence for every binding of rows and columns and for the local codes of each kind: a status (proposed, seen in the team's own queries, confirmed by a person, or confirmed by a count), where it comes from, one sentence, and, until a person or a count confirms it, the question for a person. It also holds notes on eras and further questions. `rolemap.open_items` lists every binding that is not yet confirmed, with its question, as the list that an Outline stage would work through. `fixtures/map/` is the map of the invented world, written to follow the invented conversion wherever that affects the audit: an anaesthetic is kept where its theatre case reaches a hospital visit with an admission time, its patient is the visit's patient, and a reading belongs to it through the observation sheet that carries its key. The realistic world's map is private.

**Compiling.** `rolemap.compile_query` writes an audit, or a count, with a map as one T-SQL statement: the three role views as common table expressions, each source table read `WITH (NOLOCK)`, and then the audit as written. With `blank`, the final SELECT leaves blank any count from 1 to 4, by the rule of `target.count_columns`. The compiled neonatal audit is about 180 lines, of which the three views of a map are about 35, against 400 to 700 lines for the source query that the conversion composes.

**The role-level shadow.** `rolemap.role_shadow` builds a DuckDB database that holds just the three role views as tables. It fills them from a seed with a few hundred anaesthetics over seven years, about one in seven of them neonatal, with a cuff mean every three to five minutes, an arterial mean every minute for some, and a few test patients, missing stops and values that were not accepted. It then adds the planted neonates of `rolemodel/planted_neonates.json`, which are the cases of the two neonatal scenarios written once as role rows, each with the minutes and the death that the audit must give. An audit can be written and rehearsed on this shadow before any map exists, and needs no knowledge of any hospital.

**The standard counts.** The worst errors of a map do not fail: they move children silently into the band in which nothing was recorded. `rolemap.count_queries` gives five counts, each one SELECT over the role views, so that each runs at any hospital once compiled with its map: the anaesthetics of each year with how many have a patient, a date of birth, a stop, any reading and an accepted mean pressure; the keys of each role view that more than one row holds; the readings by kind and year, with how many were accepted, hold a number and belong to an anaesthetic; the gaps between consecutive mean pressures of one kind within an anaesthetic, in bands, by year; and the mean pressures that fall before their anaesthetic's start or after its stop, by year. Every count is rounded down to ten, and a group that fewer than ten rows hold is left out. `rolemap.read_counts` turns the results into sentences. It flags a year in which a coverage figure falls to half or less of the best year's share, comparing each share at the bound that its rounding allows so that rounding alone never makes a cliff, and a year in which far more mean pressures fall outside their anaesthetic than in the best year. It also reports a kind of reading that is absent in some years, repeated keys, and a change in the commonest gap between readings.

**A result with its coverage.** `rolemap.result` runs an audit and the counts together and returns the answer with the coverage by year, the findings and, beside the band in which nothing was recorded, a sentence that says how many of its anaesthetics come from years that the counts flag. A test copies the invented map, makes the readings reachable only for anaesthetics from 2025 onwards, and confirms that the audit still runs and moves every neonate of 2023 and 2024 into that band without any error, that the counts flag both years, and that the sentence says so.

**What the prototype has shown.** On the role-level shadow, with no map, the audit gives every planted neonate its expected minutes and death, and each band moves by exactly what the cases imply. Through each world's map, on that world's existing shadow with every planted scenario in place, the compiled audit gives the same band table as the OMOP target query gives through the conversion, and the same minutes for every neonatal anaesthetic, in DuckDB and on SQL Server, and the counts agree between the two engines.

**What it does not yet do.** The map follows the existing conversion in each world, so it inherits that conversion's guesses, and nothing in it has yet been confirmed by a person or a count. The evidence is written by hand: the tool does not yet mark a binding as seen from the team's queries, or confirmed from a count's result. Only one audit has been written against the roles, and the contract holds only what that audit needs. The counts are not yet offered on the page, at the boundary or in the checklist, and the page shows nothing of the roles. No map has yet needed the shapes that the paper stress test found, such as merged patients, readings linked to an anaesthetic only by time, or a link that changed in a given year; SQL can express them as derived tables and unions, but none has been tried here. The compiled query has not been timed on a large database, and `role_reading` reads every value of the anaesthetic's record before the audit keeps the mean pressures, so its plan should be seen before it runs on a real one. The role-level shadow's values are drawn from simple distributions rather than from the realism tables that the sandbox uses.
