# Architecture review of Schemalyser, 14 October 2026

This review reads the plan of record (`docs/roadmap.md`), the architecture contract and its companion documents, and the code they point at, on branch `naive-pass` at commit 47fbae9. Nothing was run beyond short read-only commands. Line references are to the files as they stand at that commit.

The engineering below the question is sound. The layer rule in `core/tests/test_contract.py` is real and has no remaining debts, the evidence store is append-only with five dimensions kept apart, and the static policy on the final script is careful. The weaknesses are all at the new seam: the question package, the service that writes it, and the plan for getting it through the hospital. In each of those places the documents describe one system and the code builds two or three slightly different ones.

## Findings, in order of importance

### 1. The roadmap's status ladder for a package merges public and private states, which the contract forbids

**Where.** `docs/roadmap.md:66` and `:68` give the package one status with four levels (well formed, synthetic tests passed, hospital mapping supported, production validated) and say that "a package at a lower status cannot be compiled for production". `docs/contract.md:182` (invariant 5) keeps feasibility, correctness and safety apart, and `docs/contract.md:185` (invariant 8) requires that every status on the public side is a function of the package and the public contract alone.

**What is wrong.** "Hospital mapping supported" and "production validated" are facts about one hospital, not about the package. A package written once at the public service and opened at two hospitals would need two statuses at once. If the status travels with the package, or is written back to the service, it carries one bit per hospital of what that hospital supports, which is exactly the leak that invariant 8 and the A7 work of 9 October closed. A linear ladder also merges the three reports into one verdict.

**Recommendation.** Give the package a public status only: well formed under the contract, and examined (with the version of the examination it passed). Keep "supported" and "validated" in the hospital's project as the feasibility report and the evidence dimensions already record them, and never write them into the package or back to the service. The rule that a package below some level cannot be compiled for production then becomes two separate gates on the hospital side: the public status must be at least examined, and the feasibility report must show the parts it needs at a stated readiness.

### 2. There is no single definition of the question package, and the Go and Python sides disagree on almost every field

**Where.** The format exists only as a Go struct, `ask/internal/question/package.go:32-46`. No Python module reads `schemalyser-question/1` (a search of `core/`, `site/` and `tools/` finds no reader). The workspace import reads a folder of `question.sql`, `title.txt` and `note.md` (`core/schemalyser/workspace.py:109`, `:121`), and the contract still says a question arrives as "a folder validated as untrusted input" (`docs/contract.md:125`, `:166`, and the acceptance test at `:207-216`). The package build expects decisions as `{"decisions": [{"about", "decision", "by", "date"}], "exact_small_numbers"}` (`core/schemalyser/audit.py:48`), while Ask writes a list of sentences (`package.go:37`). The word "specification" now names three different things: the export's typed `schemalyser-specification/1` (`docs/specification.md:19-45`), Ask's free JSON object with "cohort, outcome and result" (`ask/internal/prompt/prompt.go:17`), and the roadmap's planned `specification.json` with "a cohort, an outcome and a result grain" (`docs/roadmap.md:66`).

**What is wrong.** The owner's decision that a package is a JSON file or an address, never a folder, has not reached the contract or the import, so the one tested import path cannot read what the service produces. Ask's "specification" is unvalidated prose in JSON clothing: nothing compiles it, nothing checks that `question_sql` implements it, and nothing in the core could read it. Calling it a specification invites the reader to believe that the first stage of compilation (specification to role SQL) is happening, when in Ask the model does that step and nothing checks it.

**Recommendation.** Write the format once, as a JSON Schema in `core/schemalyser/rolemodel/` beside the contract, embed it in the Go build as the contract is embedded, and add one Python module (`question.py`, layer 3) that is the only reader and validator of a package. Point the workspace import, the page and the workbench at it, and retire the folder form. Amend `docs/contract.md` sections 2, 4 and 7 to say "a JSON file or an address" (the contract is frozen, so record it as a dated amendment, as was done on 13 October). Decide whether Ask's specification is documentation or a typed artefact; finding 5 argues for typed decisions, and then the field should be renamed so that "specification" means only the export's compilable format.

### 3. The service's check is a regular expression, and the model is not told the shape the hospital side requires

**Where.** `package.go:157-182` checks the SQL with a word list, a `role_` prefix match and a test that the text begins with SELECT or WITH. `ask/README.md:12` says it checks "one SELECT over the roles, no invented part". The model reads a rendering of the contract that omits the mapping views and the capability catalogue (`ask/internal/rolemodel/rolemodel.go:50-58`, `:90-153`). The prompt does not mention the two-part form (`prompt.go:19`), which `compiler._cohort_cte` requires (`core/schemalyser/compiler.py:214-220`): a common table expression that reads only the anaesthetics and the patients and returns `anaesthetic_key`. The prompt tells the model that drafts may be used (`prompt.go:21`, `rolemodel.go:109`), and the role policy refuses every draft (`core/schemalyser/rolepolicy.py:124-125`).

**What is wrong.** A table that does not begin with `role_` (a mapping view, a source table, `dbo.anything`) passes the service's check unnoticed, and so do invented columns, unknown kinds and disallowed functions. The service labels such a package `drafted` and publishes it. The first time anyone learns that it is malformed is in the hospital, on the one clinician's time, which is the cost the project exists to remove. Questions over drafts, which the prompt encourages, are refused there in every case today. Without the mapping views the model cannot write any question about a particular drug, procedure or diagnosis, because `role_drug.drug` is an opaque local key. Without the catalogue, every question is bespoke SQL, which cuts against `docs/product.md:29-31`, where the catalogue is how questions grow. The service is also a surface that owns logic of its own, against invariant 9 (`docs/contract.md:186`): no command line reads or writes what it writes.

**Recommendation.** Run the core's own checks inside the service rather than re-implementing them. "Python minimal" can still allow one short-lived command in the image, such as `python -m schemalyser.question check PACKAGE.json`, which would run the role policy, the two-part form check of `workspace.py` and, later, the examination on the invented world in DuckDB, and return the failed rules to the model on the next turn. If Python in the image is refused outright, the honest alternative is to label every service status as "not yet checked" and have the page do all checking; the current middle state, a weak check presented as a check, is the worst of the three. In either case, render the mapping views and the catalogue into the prompt, state the two-part form as a rule of the SQL, and make the prompt's statement on drafts match what the policy admits.

### 4. The published address is mutable, and its hash cannot be checked by anyone else

**Where.** `/q/TOKEN` serves the latest package (`ask/internal/server/server.go:287-313`), with its hash in a response header. The hash is SHA-256 over Go's `json.Marshal` of an anonymous struct with Go field names, which escapes `<`, `>` and `&` and leaves `status` and `draft_parts_used` out (`package.go:204-218`). The roadmap requires "an address that carries its hash" (`docs/roadmap.md:72`) and the standing rules say the page's one fetch is "of a package whose hash it checks" (`:113`).

**What is wrong.** A hash supplied in a header by the same server that supplies the body proves nothing about the body. Because the address names the latest version, the package that the clinician compiles in the hospital may differ from the one the asker agreed to, if the asker carried on talking to the model afterwards. Reproducing the hash in Python would mean imitating Go's field names and HTML escaping exactly, which is fragile. The status sits outside the hash, so it can change without the hash changing.

**Recommendation.** Make each published version immutable, at an address such as `/q/TOKEN/N`, and let the address the asker hands over carry the SHA-256 of the exact bytes served, in the fragment (`#sha256=…`) so that it never reaches the server. The page then hashes the bytes it received, which needs no canonical form in either language. Keep "latest" only as a convenience for the asker's own screen.

### 5. The examination, as planned, puts the bottleneck back on one person

**Where.** `docs/roadmap.md:78` plans planted cases "for each question with their answers held out", and `:80` requires that each question passes them. `docs/contract.md:105` requires that expected rows are written independently of the work they judge.

**What is wrong.** For catalogue capabilities this is right. For free questions from fifty anaesthetists, someone must write independent planted cases and expected answers for every question, and the only candidates are the owner or the one clinician. The model cannot write them, because then they are not independent. Step 1 has the same weakness in small: the owner writes both the role query and the "hand-written" comparison query against the stand-in (`docs/roadmap.md:54`), so agreement shows consistency of one person's reading, not correctness.

**Recommendation.** Make the decisions typed rather than free sentences: an age bound in days, a period, exclusions by name, the grain, the statistic, the treatment of duplicates and of missing values. From typed decisions the examination can generate its own boundary cases (a patient one day either side of each age bound, a duplicated reading, a reading on another encounter, a test patient) and check the answer without a hand-written expected row per question. Keep hand-written held-out cases for the capabilities of the catalogue, and give a free question a lower public status ("examined by the generated suite") than a capability ("examined against held-out cases"). Where possible, steer free questions towards parameters of existing capabilities, so that the hand-written cases are reused.

### 6. Promotion of draft parts is gated in three places that do not agree, and the plan for it touches only one

**Where.** The role policy gates on `status == "contract"` (`rolepolicy.py:54`, `:124`). `rolemap.views()` gates on a separate `required` flag (`core/schemalyser/rolemap/__init__.py:231-234`). The two-part compiler reaches only three parts, from a hard-coded table (`compiler.py:27-28`), and refuses any other part as "unreached" (`:233-234`). `compile_query` and `check_audit` admit every part, drafts included (`compiler.py:79-87`), and `audit build` does not call the role policy at all; only the workspace import and the export do (`core/schemalyser/audit.py:549-575`). `contractcheck.py:30` knows two statuses. The roadmap's step 2 (`docs/roadmap.md:60-62`) defines done as the status, the checker and the policy.

**What is wrong.** Promoting a part under step 2 as written would let the policy admit it while the compiler still refuses it, and whether a draft is admitted at all depends on which command a person happens to run. The parts that matter first (fluids for the transfusion question, drugs, techniques) carry `stay_key` with an empty `anaesthetic_key` where the source records only the stay (roles.md, rule 13), and `#cohort` carries no stay, so the two-part script cannot reach those rows by key even after promotion. The "rehearsed" status also lowers the bar that `docs/contract.md:27` sets (validated at a hospital, and not before) on evidence that is a naive map agreeing with a reference map written for the same synthetic stand-in. That shows the part can be mapped from the vendor's published shape; it says nothing about clinical meaning, which the external review of 8 October named as the gap.

**Recommendation.** Derive every gate from one field of `contract.json`, read through one function, and delete `required` and the hard-coded `REACHED` (the links in the contract already say how each part is reached). Extend step 2's definition of done to the compiler, the coverage step and the stay route: `#cohort` must carry the stay where any part needed is reached by it, and the policy's coverage step must count it. Treat "rehearsed" as what it is, a statement that a part maps cleanly on the stand-in, and allow it for examination and for compilation on the stand-in only, never for a production package, until the contract amendment that admits it is written and dated.

### 7. Evidence goes stale for the wrong reasons, and packages cannot tell when a draft has changed

**Where.** `rolemap.part_hashes` (`rolemap/__init__.py:156-175`) hashes the whole view object, including `status`, `title`, `description`, `look_for`, `holds` and `omop`, with every word and meaning of every vocabulary its columns name, and for readings every reading kind. Each binding's evidence rests on that hash. The contract lets a draft's columns change without a new version (`contract.json`, `versioning`), and a package records only `contract_version` (`package.go:35`).

**What is wrong.** Correcting a description, adding a search word for the proposer, adding a new reading kind, or promoting a part from draft to contract makes every binding of that part stale in every saved hospital schema, although nothing the binding rests on has changed. Promotion, in particular, would mark the evidence of the parts being promoted as stale at the moment they are promoted. In the other direction, a draft whose column is renamed under the same version 1.1 leaves every package that reads it apparently current.

**Recommendation.** Hash a semantic projection of each part: its name, key, links and columns with their type, vocabulary, mapping and optionality. Let vocabulary changes stale only the code-translation dimension of the column that uses them, not every binding of the part. Give each part an integer version in `contract.json`, checked by `contractcheck` against a committed lock of the semantic hashes so that a change cannot be made without a bump, and have the package record the version of each part it reads. The page can then refuse a package whose part versions it does not hold, rather than relying on the contract's overall number.

### 8. The documents describe two different products, and number the layers two different ways

**Where.** `docs/product.md:39` says that "there is no general query builder" and that most computation is done by the clinician over exported rows (`:29`). Ask is a general query builder by language model. `docs/architecture.md:20-22` and `docs/screens.md` place compilation in the workbench's export screen, while `docs/roadmap.md:72` places it on step 1 of the offline page. The roadmap's layers (`docs/roadmap.md:15-20`: 3 questions, 4 examination, 5 compilation, 6 service) do not match the contract's (`docs/contract.md:47`, `:63`, `:83`: 3 compilation, 4 test worlds, 5 surfaces), which `LAYERS.toml` enforces, and `docs/ask.md:3` calls Ask "layer six".

**What is wrong.** A reader cannot tell whether the product is the export with a catalogue or free questions through a model, and the roadmap now builds the second without retiring the first. Two hospital-side surfaces would each compile packages, which doubles the work and the tests. "Layer 3" now means two different things depending on the page.

**Recommendation.** Write one paragraph in `docs/product.md` that says how the export, the catalogue and free questions relate (my suggestion: a free question is either answered from an export of sections, or becomes a capability, and a bespoke aggregate is the exception), and choose one hospital-side surface for compiling a package. Rename the roadmap's six items by name rather than number, or amend the contract's numbering, so that one scheme is used everywhere.

### 9. Fetching a package by address breaks the page's simplest guarantee unless the order is enforced

**Where.** The page's policy is `connect-src 'self'` (`site/index.html:10`), and the worker checks that another site is refused before it starts (`docs/architecture.md:107`). `docs/contract.md:166` says that a package reaches the private side "through a mechanism the hospital approves".

**What is wrong.** A fetch from the service needs the policy relaxed to admit the service's origin, and the worker's self-check changed to match. The guarantee today is that nothing can leave; afterwards it is that nothing can leave except to one origin, which is only safe if no private material is loaded at the time. A fetch is also a mechanism the hospital has not approved, and it pulls text from an internet-facing service whose content a language model wrote into the environment where production SQL is prepared.

**Recommendation.** Keep the file as the default and the address as the convenience, not the other way round. If the address is kept, pin the service's origin at build time, allow the fetch only in the state before any dictionary, schema or paste is loaded (enforced by the core's state, not by the page's script), and verify the fragment hash of finding 4 before anything parses the body. Ask the hospital's information security team to approve the mechanism, as section 4 of the contract requires.

### 10. The service is an inbound channel for hospital information, which the documents do not acknowledge

**Where.** `docs/ask.md:7` says the standing rule "holds because the service has nothing of a hospital to show one". `docs/workspace.md:50-52` already says that a question about an identifiable patient is clinical content. The `cli` backend runs the developer's Claude Code command line with the developer's environment and working directory and nothing that removes its tools (`ask/internal/model/cli.go:43-46`).

**What is wrong.** Fifty clinicians typing free text will sometimes type a patient's details, an undisclosed incident, or the name of a table they have seen in the clinical system. That text goes to an external model and is stored on a server outside the hospital. The invariant that no model sees hospital material is then kept only by the users' care. During development, the `cli` backend gives the model whatever tools and settings the developer's own installation allows, in a working directory inside a repository that has the private reference folder beside it, with untrusted clinician text as the prompt.

**Recommendation.** State the rule on the service's first screen in the house voice, screen messages before they reach the model for record numbers, dates of birth and upper-case table-like names (the Go test at `rolemodel_test.go:11` already has that pattern), and record the hospital's approval of the service under its AI policy. Run the `cli` backend with tools and external servers disabled, in an empty temporary working directory, and with the developer's settings and memory excluded.

### 11. T-SQL as the public dialect is the right choice; the planned portable dialect is the wrong remedy

**Where.** `docs/roadmap.md:84-86` plans a subset that round-trips to DuckDB and SQL Server. The role policy parses in the SQL Server dialect and reuses the final-script allowlist (`rolepolicy.py:16`, `core/schemalyser/policy.py:75-78`). The compiler writes only T-SQL, with `WITH (NOLOCK)`, `#cohort` and `dbo` (`compiler.py:30-35`).

**What is wrong.** The production target is SQL Server, the agents already write T-SQL, and the allowlist is already a dialect in all but name. The real risks are semantic, not syntactic: SQL Server's usual case-insensitive collation against DuckDB's case-sensitive comparison of kind words, `DATEDIFF` counting boundaries, integer division, and `ANSI_WARNINGS OFF`. A subset that "round-trips" will parse identically on both engines and still give different answers. The allowlist has no median, which the roadmap's first question needs and the prompt promises (`prompt.go:19`), so the model must hand-build one from `ROW_NUMBER` and a windowed `COUNT`. Separately, the second stage is fixed to SQL Server, which matters for OMOP as a source wherever the core OMOP runs on another engine.

**Recommendation.** Keep T-SQL as the authoring dialect and call the allowlist the dialect. Decide the median once (either admit `PERCENTILE_CONT` with a window, or give a catalogue capability that computes it) and say so in the prompt. Put the effort of step 6 into running every examination on both engines through the existing harness and comparing answers, and into fixing kind comparisons to a binary collation in the compiled SQL. Record the second stage's engine as a property of the hospital schema, so that a later OMOP source on another engine has a place to declare it.

### 12. Both OMOP routes are thinner than the documents suggest

**Where.** `docs/contract.md:55` makes the route over the roles "the route for all new work". In the public conversion, `fixtures/conversion/conversion.json` has nineteen direct steps and one over the roles. A step over the roles may read any part, drafts included (`core/schemalyser/conversion.py:632-649` reads `rolemap.public_views()`). For OMOP as a source, `roles.md` (the OMOP table near line 663) says that `role_reading` adds the link by record that OMOP lacks, that `role_patient.is_test` has no OMOP home, and that operations in OMOP are told apart only by time.

**What is wrong.** The draft gate applies to questions and not to conversion steps, so the OMOP layer can ship rows from parts that no audit may read. As a source, an arbitrary hospital's OMOP cannot meet rule 3 of the record unless its measurements carry a visit detail per anaesthetic, which in practice only an OMOP filled by this project's own anaesthesia layer does. Step 8 (`docs/roadmap.md:96-98`) proposes exactly that round trip, which is a useful consistency test but not evidence that OMOP works as a source for anyone else.

**Recommendation.** Apply the same part gate to conversion steps over the roles as to questions. Rename step 8's first half as the round-trip test it is, and write down which OMOP conventions (visit detail per anaesthetic, test patients retained, measurement linked to visit detail) a third-party OMOP must meet before a hospital schema can bind the contract parts to it.

### 13. Layer 1 has no reader of its own

**Where.** `contract.json` is loaded through `rolemap` (`rolemap/__init__.py`, layer 2 in `LAYERS.toml:28`), and `contractcheck.py` is the only layer-1 module. The Go service has its own reader (`rolemodel.go`).

**What is wrong.** Every consumer of the contract imports the hospital-schema layer to read it, so the dependency rule is satisfied in form while layer 1 is effectively part of layer 2. The functions that the Go service must mirror (`contract`, `views`, `statuses`, `capabilities`, `mapping_views`, `part_hashes`) are mixed with map reading and writing.

**Recommendation.** Move the contract's readers into a layer-1 module, which is also the natural home of the gate of finding 6, the part versions of finding 7 and the package schema of finding 2.

### 14. Smaller drift and hardening

- `docs/success.md:31` reports nine parts identical through the naive schema and "the other nine" as drafts, while `docs/roadmap.md:34` and `:60` report sixteen. `docs/architecture.md:89` still gives 13 of 16 bindings from an older measure. One of these is wrong, and the roadmap's promotion list depends on which.
- `docs/architecture.md:20-22` lists the audit screen as "to come", while the workbench's export screen is built.
- `ask/internal/rolemodel/rolemodel_test.go:14-17` skips silently when the repository's contract is not beside it, and the repository now holds two copies of `contract.json`. Generate the embedded copy at build only and do not commit it.
- `package.go:165` rejects words such as CREATE inside comments and string literals, and the one-statement check strips only line comments, so a block comment or a semicolon inside a literal gives a false refusal.
- The Caddy snippet (`ask/deploy/ask.caddy:5-7`) passes a client's `Remote-Email` header through on `/q/*`. The handler there does not read it, but stripping it on that route costs one line and removes the question.

## What I would change in the roadmap

1. **Before step 1, add a step 0 of seams.** Write the package's JSON Schema and the Python reader, amend the contract's sections 2, 4 and 7, make published versions immutable with a fragment hash, move the contract readers to layer 1, and derive the part gate from one field. Without this, steps 1 to 4 each build against a moving format.
2. **Change step 1's question to one over the three contract parts**, so that it proves the new path (package to page to compiled script to stand-in) in a morning. Make the transfusion question the acceptance test of step 2 instead, because it needs a draft part, the stay route and a median. Have someone other than the owner write the comparison query, or say plainly that step 1 shows consistency rather than correctness.
3. **Extend step 2's definition of done** to the compiler's reach, the stay route in `#cohort` and the coverage step, the semantic part hash, per-part versions, and the same gate for conversion steps. Keep "rehearsed" out of production packages, and record the contract amendment with its date.
4. **Rewrite step 3's statuses** as one public status (well formed, examined by the generated suite, examined against held-out cases) and leave support and validation to the hospital's own reports. Make the decisions typed.
5. **Move the measurement of step 7 forward to sit after step 3.** Ten questions through the service, checked by the real role policy and compiled through the realistic pass's schema, will say within a day whether the model's output is usable, which decides how much of steps 4 to 6 is worth building. Gate `/q` publication on a passed check from then on.
6. **Rewrite step 5** so that free questions are examined by suites generated from typed decisions, and held-out planted cases are written per capability.
7. **Shrink step 6** to the decisions on median and collation and to cross-engine runs of every examination; drop the round-trip subset.
8. **In step 4, make the file the default** and the address a pinned, hash-checked convenience allowed only before private material is loaded, with the hospital's approval of the mechanism. Choose one hospital-side surface for compiling a package and retire the other.
9. **Re-scope step 8** as a round-trip test, and add a written list of the conventions a third-party OMOP must meet before it can serve as a source.
10. **Add to the decisions for the owner:** what the product is (export with catalogue, free questions, or both, and how they relate), whether the service may run one short Python check, and the rule and screening for patient details typed into the service.
