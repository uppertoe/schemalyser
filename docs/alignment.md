# Bringing the code to the contract

This page records where the code stands against `docs/contract.md` on 9 October 2026, and what has to change to bring it into line. Six readings were made, one for each layer, one for the surfaces and the adapters, and one for the test suite and the dependency rules, each clause by clause with file and line evidence. This page keeps the conclusions and the order of work; the evidence is cited by file so that it can be checked.

The register is in the four classes the work runs in, in order: behaviour and logic first, then tests, then integration, then the surfaces. Within each class the contradictions come first, because the code there does something the contract forbids, then what is missing, then what is partly there. An item is done when the contract's clause is true of the code and a test says so.

## The verdict in short

The strongest parts are the testbed, the workspace export's allowlist, the static policy on the final text of the script, and the three contract parts themselves, which are vendor-free and in step with their prose. The audit path from a question over the roles to an execution package exists and is honest in its wording.

The weakest parts are the three the contract leans on most. The saved hospital schema is not yet an evidence store: it has no version identity, its journal overwrites rather than appends, and the five evidence dimensions are collapsed into one status and a computed ladder. The OMOP conversion is entirely on the direct route, with nothing recording that, and the clinical logic the contract places over the roles sits in direct steps, one of which invents an end time for an infusion with no recorded stop. And the planted scenarios that judge an agent's work are shipped in the workspace, so nothing is held out.

Two tests of the contract fail on the working tree today: one module declares no layer, and the testbed loads a file from `tools/` by path. Those are the first two things to fix.

## The order of work

The register is worked in its four classes in order, with two exceptions taken first because they are small and the contract test is red until they are done: B1 and the pinning of the known debts in B2.

Within behaviour and logic the order is the record, then the roles, then compilation and conversion, because each rests on the one before:

1. **The record.** A6, A5, A24, A13, A14, A15. When these are done the saved schema is a versioned, append-only evidence store with five dimensions, scope, actor and invalidation, and an import by which results return.
2. **The roles.** A10, A11, A12, A3, A4, then A2. When these are done the contract has mapping views, source kinds and versioned capabilities, the drafts hold no local code, and the window correction is gone.
3. **Compilation and conversion.** A16, A17, A18, A19 with A1, A20, A23, A7, A26, A27. When these are done feasibility makes its two claims, the policy requires the series, every step records its route, the first step reads the roles and treats a missing stop honestly, the manifest can carry an approval, and the status leaks nothing.
4. **The surfaces' logic.** A25, A8, A9, A22.

Then the tests of section B, then the integration of section C, then the surfaces of section D. The two acceptance tests of B7 are written early as failing tests, so that each phase is seen to move them.

After both acceptance tests pass, and before any draft part beyond the drug part is promoted, the abstraction is tested against a second, publicly documented source. A small mapping from OpenMRS, whose schema is public and openly licensed, is written to the roles beside the invented hospital's; one audit and one conversion step written over the roles run unchanged against planted histories in both; and every source-specific exception the public logic needed is recorded. If the public SQL runs unchanged the roles are doing what they promise, and if it has to change for each source the normalisation boundary is not yet expressive enough.
