# The workbench

The workbench is a local web server over a project folder. It keeps the saved hospital schemas, the questions, the audits, the exports of the anaesthesia record and the runs of the test on made-up rows in one place, starts the core's commands, and renders the reports they write. The offline page, Describe the record, stays separate and unchanged, and the workbench serves a built copy of it at `/describe/` when one exists.

    python -m schemalyser.workbench --project FOLDER [--port 8765]

Run from `core/`, it needs the packages that `tools/workbench/requirements.txt` pins. The image in `tools/workbench/` holds them, and its README says how to build and run it.

## The project folder

The project folder is a plain folder, which the hospital may keep as a git repository.

- `workbench.json` holds the folder's name and the tool's version, and nothing else.
- `schemas/` holds saved hospital schemas, such as `hospital-schema-SCHEMA_ID.schemalyser.zip`, whose name carries the version. The workbench refuses to replace a saved schema with a different version under the same name.
- `questions/` holds one `.sql` file for each question over the parts of the record, with its title as the leading comment.
- `audits/NAME/` holds one audit: the request, the clinicians' decisions, the log of the build, any estimated plans, and `package/`, which is the folder that `schemalyser.audit build` wrote and that goes to the database analyst.
- `runs/NAME/` holds one run: its settings in `run.json`, its log, and `out/`, which is the folder that `schemalyser.testbed run` wrote.
- `exports/NAME/` holds one export of the anaesthesia record: `request.json`, with the saved hospital schema it reads, the episode list's form, count and hash, the rule for patient and date pairs, and the latest version of the schema that an evidence import saved; `episodes.csv`, the private episode list; `specification.json`; `support.json`, the feasibility report over every section, kept with the hash of the schema it was read from; the log of the compilation; `package/`, which `schemalyser.audit export` wrote; `returned/SECTION/`, the files that the database analyst returned; and `results/SECTION-TIME/`, each a results package that `schemalyser.results write` wrote.
- `specifications/` holds the specifications saved for reuse. They hold no hospital material and may be shared.
- `.tmp/` holds temporary files, which may be deleted once the workbench is closed.
- `.cache/` holds the working copy of the Athena vocabulary that a run makes. The testbed keeps its working copy beside the folder it reads, so a run reads an Athena download that lies outside the project through `.cache/athena/`, a folder of links to the download's files, and the copy is made in `.cache/athena-working-copy/`. The download itself is only read. The cache may be deleted, and the next run with the Athena vocabulary builds it again.

Everything the workbench writes stays in the project folder, because a saved hospital schema and anything made from it name the hospital's tables.

## The screens

- **The overview** lists the saved hospital schemas, with the readiness of the three parts the audits read and the scoreboard's first line, then the questions, the audits and the runs, with forms to add each.
- **What a question needs** reads a question against a saved hospital schema and shows the verdict, each requirement with its state, and the evidence requests with their SQL ready to copy. With no question chosen, it shows the programme of every question in the project.
- **An audit** builds the execution package from a question and a saved hospital schema, with an optional period, decisions and the name of the clinician who made them, then shows the class and what it needs, the README, the specification, the script, the safety report by rule, the answer on made-up rows, a form for the estimated plan, and the manifest's hashes. If `query.sql` has changed since the build, the page says that the review is voided.
- **The export** is screen 2 of `docs/screens.md`, the anaesthesia record export, in eight steps on one page, each of which names who acts and draws on a report or command of the core.
  1. *The hospital schema.* `feasibility.sections` assesses each section of the anaesthetic record as the export compiles it, and each measure of the catalogue, against the saved hospital schema: the part's own state, the lowest state of what the section needs, the readiness in its three states, and the smallest piece of work for each section that falls short. It is also `python -m schemalyser.feasibility sections SCHEMA.zip`.
  2. *The episodes.* The clinician gives the list as a file of anaesthetic keys, or of patient and date pairs with the window in hours and the rule for several anaesthetics. `specification.read_episodes` reads it, and the export records its form, count and hash. Once the database analyst returns the result of the section `episode_resolution`, `python -m schemalyser.results show` gives the share of pairs resolved to exactly one anaesthetic and the ambiguous pairs, and a count that the result leaves blank stays blank.
  3. *The sections.* `specification.choices` offers the parts of the record as a tree in the clinician's words, each with its kinds, its window relative to the anaesthetic's start and stop, and its flags. A part that the hospital schema does not map, or that the role model cannot yet join to an episode, is shown as not currently mapped with its piece of work and cannot be chosen, and neither can a kind whose codes the schema does not hold.
  4. *The derived sections.* The catalogue's measures, with each parameter as a field and each table parameter, such as the thresholds by age band and the factors by agent, as a grid. The catalogue gives no defaults yet, so the fields start empty and the screen says so. A measure that needs what the schema does not map is not currently supported, with its evidence request, and one that the catalogue declares without SQL cannot be chosen.
  5. *The output.* Rows or an aggregate, how the keys are identified, and which sections may leave, with the notes left in unless named, and the sentence that an export of rows is identifiable data whose leaving is the hospital's approval.
  6. *The specification.* `specification.from_form` writes the specification from the form's fields, which is also `python -m schemalyser.specification write FIELDS.json --out SPEC.json`. A specification that breaks a rule is kept as chosen and its rules named, and no package is compiled from it. The clinician saves it to `specifications/` and loads a saved one, or a file, into another export.
  7. *The package.* One action runs `python -m schemalyser.audit export`. `audit.export_status`, also `python -m schemalyser.audit export-status`, gives for each section its outcome, the feasibility report's verdict with its two claims named apart, the SQL over the parts of the record, the series after each step of which the database analyst can stop, the class and the policy's outcome, and the manifest. The database analyst records approval or refusal with their name through `audit.approve`, and the screen shows when a change has voided it.
  8. *The results.* The outcome and the plan that the database analyst returns enter the hospital schema through `python -m schemalyser.describe import-evidence`, each import reading the version that the one before saved, and the new version is kept in `schemas/` while the package still binds to the schema it was compiled from. The result becomes a results package through `python -m schemalyser.results write`, which writes one only for an approved package, and the screen reads it with `python -m schemalyser.results show` and shows its shape against the expected columns, the coverage of the record for the period and what was rounded or suppressed.
- **The test on made-up rows** starts a run and lists the runs with their outcomes. A run's page shows the summary, the checks, the planted scenarios, the four groups of the reconciliation, the gates and counts, the Data Quality Dashboard and release equivalence. Each scenario and discrepancy links to the steps behind it, and a step's page shows its reconciliation and its SQL.

## How the workbench calls the core

The audit's build, the export's package, the plan review and the test on made-up rows run as subprocesses of `python -m schemalyser.audit` and `python -m schemalyser.testbed`, with their output in the job's own folder, and the export's evidence imports and results packages as short subprocesses of `python -m schemalyser.describe` and `python -m schemalyser.results`. While a command runs, htmx asks for its progress every two seconds and shows the end of `log.txt`; once it has finished, the server tells the page to reload, and the page shows the report. The feasibility report, the programme, the readiness, the scoreboard, the export's choices and its status write nothing of their own, so the workbench calls the core's functions for them directly, through `project.py` where the function lies in a module that the workbench does not import. Whether a package still stands is read with `audit.status`, which is also `python -m schemalyser.audit status FOLDER`.

## What the workbench never does

The workbench listens on 127.0.0.1, refuses a request whose Host is not this computer and a form from another site, and forbids its pages any other connection. It listens on 0.0.0.0 only inside its container, which it recognises by the file `/.dockerenv` that Docker writes at the root of every container; elsewhere it refuses `--host 0.0.0.0` and says why. The image in `tools/workbench/` needs nothing further, and compose publishes its port on 127.0.0.1 alone. It makes no request of its own and serves htmx and Alpine.js itself. It never connects to a hospital database: the database analyst runs the package under the hospital's own controls. Every verdict, class, state and outcome on its pages comes from a report that the core wrote, read by name: the scoreboard's overall line is the one that the core's wording for it opens, and the planted cases are summed up by the verdict that the correctness report gives them. A decision is recorded with the name that the form gives, and as "not recorded" when the form leaves it empty; the workbench never supplies a name of its own.

`core/tests/test_export_screen.py` checks each step of the export screen on the invented world, the words of the screen against the owner's vocabulary, and that nothing is written outside the project folder. `core/tests/test_workbench.py` checks each other screen on the invented world, the voided review, the author of a decision, the refusal of another site's form and of another host by the workbench's own list of trusted hosts, the refusal of 0.0.0.0 outside a container, and that nothing is written outside the project folder or beside an Athena download.
